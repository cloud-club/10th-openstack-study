# Part A — 필수

## A1. 이번 주에 하는 일

- **이론**: "인스턴스 생성" 버튼 하나가 내부에서 통과하는 6단계를 배웁니다
- **실습**: 배포받은 가비아 VM에 SSH로 접속하고, 서버 상태를 명령어로 검증합니다
- **완료 기준**: SSH 접속 성공 + 환경 확인 명령 출력 스크린샷을 다음 세션 전까지 단톡방 인증

한 가지 미리 말해둘 것 — 여러분이 이번 주에 "받는" VM은, 스터디장이 가비아 콘솔에서 버튼을 눌러 만든 것입니다. 버튼을 누르면 몇십 초 뒤 IP가 달린 서버가 나옵니다. 그 몇십 초 동안 무슨 일이 있었는지가 오늘의 이론이고, **6회차에는 같은 일이 여러분이 직접 배포한 OpenStack 안에서 일어나는 걸 로그와 컨테이너로 직접 보게 됩니다.** 이번 주는 손님 입장에서 결과만 받고, 3주 뒤엔 사장 입장에서 과정을 봅니다.

## A2. 이론 — "인스턴스 생성" 버튼 뒤의 6단계

2회차에서 배운 부품들(Keystone, nova-api, scheduler, conductor, compute, Glance, Neutron, libvirt)이 전부 등장합니다. 기억이 흐리면 2회차 자료 A4를 먼저 복습하세요.

```
1. 인증        Horizon/CLI → Keystone: 토큰 발급
2. 접수        nova-api: 요청 수신, DB에 레코드 생성 (상태 BUILD)
3. 배치 결정   scheduler: Placement 조회 → Filter/Weigh → 노드 확정
4. 작업 수신   nova-compute: RabbitMQ로 지시 수신
5. 준비물 수집  Glance(이미지) · Neutron(포트/IP) · Cinder(볼륨)
6. 기동        libvirt → QEMU: VM 프로세스 실행, 상태 ACTIVE
```

### 단계별 상세

**1단계 — 인증 (수 초 미만)**
어떤 요청이든 첫 관문은 Keystone입니다. ID/비밀번호(또는 저장된 크리덴셜)로 토큰을 발급받고, 이후 모든 API 호출에 `X-Auth-Token` 헤더로 첨부합니다. 토큰에는 "누가, 어느 프로젝트에서, 어떤 권한으로"가 암호화되어 들어 있습니다.

**2단계 — 접수 (수 초 미만)**
nova-api가 요청을 받으면 토큰을 검증하고, 요청 내용(이미지는 뭘로, 크기는 어떤 걸로, 네트워크는 어디에)의 형식을 확인한 뒤, **곧바로 DB에 인스턴스 레코드를 만들고 상태를 `BUILD`로 기록합니다.** 이 순간부터 대시보드에 인스턴스가 보입니다 — 아직 아무것도 실제로 만들어지지 않았는데도요. "화면에 보이는 것"과 "실제로 존재하는 것"의 간극이 여기서 처음 생기고, 이 간극이 클라우드 트러블슈팅의 출발점이 됩니다.

**3단계 — 배치 결정 (수 초)**
scheduler가 "이 VM을 어느 물리 서버에 놓을까"를 계산합니다. 먼저 Placement에 각 노드의 잔여 자원(vCPU, 메모리, 디스크)을 조회하고, **Filter**로 조건에 안 맞는 노드를 탈락시킨 뒤(메모리 부족, 디스크 부족 등), **Weigh**로 살아남은 후보에 점수를 매겨 한 대를 고릅니다. 우리 6회차 환경은 all-in-one(노드 1대)이라 고를 게 없지만 경로는 동일하게 지나갑니다.

**4단계 — 작업 수신 (즉시)**
결정이 내려지면 해당 노드의 nova-compute에게 RabbitMQ로 작업이 전달됩니다. 2회차에서 배운 `cast`(비동기) 방식입니다 — 던져놓고 기다리지 않기 때문에, api는 이미 다음 요청을 받고 있습니다.

**5단계 — 준비물 수집 (수십 초, 시간이 실제로 걸리는 구간 ①)**
nova-compute가 세 곳에 요청을 보냅니다:

- **Glance**: 부팅 이미지 다운로드. 처음 쓰는 이미지는 네트워크로 받아와야 해서 오래 걸리고, 한 번 받은 이미지는 로컬에 캐시되어 두 번째부터는 빠릅니다
- **Neutron**: "포트 하나 만들어 줘" — 가상 NIC에 해당하는 포트가 만들어지고 MAC 주소와 IP가 할당됩니다
- **Cinder**: 볼륨을 붙이는 경우에만

**6단계 — 기동 (수십 초, 시간이 걸리는 구간 ②)**
준비물이 모이면 nova-compute가 libvirt에게 VM 정의(XML)를 넘기고, QEMU 프로세스가 뜹니다. 상태가 `BUILD` → `ACTIVE`로 바뀌면 완료. 게스트 OS 부팅은 그다음 이야기라, ACTIVE가 됐어도 SSH가 붙기까지는 OS 부팅 시간만큼 더 걸립니다.

### 이 6단계에서 가져갈 관점

1. **빠른 구간과 느린 구간이 나뉩니다.** 1~4는 "결정"이라 수 초, 5~6은 "실물 준비"라 수십 초 이상. 인스턴스 생성이 느리면 의심할 곳은 5~6입니다.
2. **모든 단계가 로그를 남깁니다.** 요청마다 `req-` 로 시작하는 request-id가 부여되고, 이 ID가 여러 서비스의 로그에 공통으로 찍힙니다. 7회차 심화 미션이 이 ID로 6단계를 로그에서 추적하는 것입니다.
3. **가비아도 같은 일을 합니다.** 스터디장이 여러분 VM을 만들 때 가비아 내부에서도 (구현은 달라도) 본질적으로 같은 단계가 돌았습니다. 오늘 배운 게 "OpenStack 지식"이 아니라 "클라우드가 동작하는 방식"인 이유입니다.

## A3. SSH — 원리를 알고 접속하기

실습 전에 SSH가 뭘 하는 건지 이해하고 갑니다. "붙는 법"만 알면 에러가 났을 때 아무것도 못 하지만, 원리를 알면 에러 메시지가 읽힙니다.

- *SSH(Secure Shell)**는 원격 서버의 터미널을 암호화된 채널로 쓰게 해주는 프로토콜입니다(기본 포트 22). 인증 방법이 두 가지인데, 비밀번호 방식과 **키페어 방식**이 있고 클라우드는 거의 항상 키페어를 씁니다.

**키페어의 원리** — 수학적으로 짝지어진 두 개의 키를 만듭니다:

- **공개키(public key)**: 자물쇠. 서버에 등록됩니다 (`~/.ssh/authorized_keys` 파일)
- **개인키(private key)**: 열쇠. 내 노트북에만 있습니다 (`.pem` 파일)

접속하면 서버가 "이 자물쇠를 열 수 있는지 증명해봐"라는 문제를 내고, 개인키를 가진 쪽만 풀 수 있습니다. 비밀번호처럼 네트워크로 비밀 자체가 전송되지 않아서 안전합니다. **개인키가 유출되면 그 서버는 뚫린 것과 같으므로**, 키 파일을 단톡방 같은 곳에 올리는 일은 절대 없어야 합니다.

**우리 상황에 적용하면**: 스터디장이 VM을 만들 때 여러분 몫의 키페어를 생성해 공개키를 VM에 넣어두고, 개인키 파일을 **개별 DM**으로 전달합니다. 세션 밖 지원용으로 스터디장의 공개키도 함께 등록되어 있습니다(원치 않으면 `~/.ssh/authorized_keys`에서 삭제 가능). (VM 첫 부팅 때 공개키가 어떻게 서버 안에 들어가는지가 Part B의 cloud-init 이야기입니다.)

## A4. 실습 — 접속과 검증

접속 정보(공인 IP, 개인키 파일, 계정명)를 개별 DM으로 받은 뒤 아래를 순서대로 진행합니다. 명령은 macOS/리눅스 터미널과 Windows PowerShell에서 동일하게 동작합니다(Windows 10 이후 OpenSSH 내장).

**① 키 파일 권한 설정 (macOS/리눅스만)**

```bash
chmod 600 ~/Downloads/mykey.pem
```

SSH는 개인키 파일이 다른 사용자도 읽을 수 있는 권한이면 접속을 거부합니다(`WARNING: UNPROTECTED PRIVATE KEY FILE!`). 600은 "소유자만 읽고 쓸 수 있음"이라는 뜻입니다. Windows는 이 단계가 없습니다.

**② 접속**

```bash
ssh -i ~/Downloads/mykey.pem ubuntu@<공인IP>
```

- `-i`: 사용할 개인키 지정
- `ubuntu`: Ubuntu 클라우드 이미지의 기본 계정명
- 첫 접속 시 `The authenticity of host ... can't be established` 질문이 나오는데, "이 서버를 처음 보는데 믿을래?"라는 뜻입니다. `yes`를 입력하면 서버 지문이 내 컴퓨터의 `~/.ssh/known_hosts`에 저장되고 다음부터 안 묻습니다.

**③ 서버 검증 — 접속되면 아래 명령을 차례로 실행**

```bash
lsb_release -a        # OS 확인: Ubuntu 24.04인가
nproc                 # vCPU 개수
free -h               # 메모리 (16GB 근처인가)
df -h /               # 루트 디스크 여유 공간
egrep -c '(vmx|svm)' /proc/cpuinfo   # 중첩 가상화 지원 여부
ip a                  # 네트워크 인터페이스와 IP
```

마지막에서 두 번째 명령이 중요합니다. 결과가 **1 이상이면 중첩 KVM 사용 가능, 0이면 QEMU 에뮬레이션 모드**입니다(2회차 A4 참고). 0이어도 실습에는 지장 없지만, 6회차에 인스턴스 부팅이 느린 이유가 바로 이 숫자입니다. 세션에서 전원 결과를 모아 비교해봅니다.

**④ 인증**: ②의 접속 성공 화면 + ③의 출력이 보이는 스크린샷을 단톡방에 올리면 3회차 완료입니다.

### 자주 만나는 에러와 의미

| 메시지 | 뜻 | 조치 |
| --- | --- | --- |
| `Permission denied (publickey)` | 키가 틀렸거나 계정명이 틀림 | `-i` 경로, 계정명(ubuntu) 확인 |
| `UNPROTECTED PRIVATE KEY FILE` | 키 파일 권한이 너무 열려 있음 | `chmod 600 <키파일>` |
| `Connection timed out` | 네트워크가 서버까지 못 감 | IP 오타, 방화벽(22번 포트), 내 네트워크 확인 |
| `Connection refused` | 서버까진 갔는데 22번에서 응답 거부 | 서버 부팅 직후면 잠시 대기 |

timed out과 refused의 차이를 기억해두세요 — **timed out은 "길이 막힘"(방화벽·IP 문제), refused는 "도착했는데 문전박대"(서버 쪽 서비스 문제)**입니다. 이 구분 하나로 트러블슈팅 방향이 절반으로 줄어들고, 5회차 이후 계속 써먹습니다.

# Part B — 심화

## B1. 인스턴스 상태 전이 — BUILD에서 ACTIVE까지, 그리고 ERROR

인스턴스 상태는 6단계 진행에 따라 이렇게 움직입니다:

```
BUILD (scheduling) → BUILD (networking) → BUILD (spawning) → ACTIVE
                                                          ↘ ERROR
```

- **scheduling**: 3단계 진행 중 (자리 찾는 중)
- **networking**: 5단계 중 Neutron 포트 작업
- **spawning**: 6단계, QEMU 기동 중
- **ERROR**: 어느 단계든 실패하면 이 상태로. 대시보드에서 인스턴스를 클릭하면 fault 메시지에 실패 사유가 남습니다

알아둘 패턴: **`No valid host was found`** 에러는 3단계(scheduler)에서 모든 노드가 Filter에 탈락했다는 뜻입니다. 자원 부족(메모리·디스크)이 대부분의 원인이고, all-in-one 환경에서 인스턴스를 여러 대 만들다 보면 6회차에 실제로 만날 수 있는 에러입니다. 이 메시지를 보면 "서버가 고장났다"가 아니라 "자리가 없다"로 읽어야 합니다.

## B2. cloud-init — 내 공개키는 어떻게 서버 안에 들어갔나

A3에서 "스터디장이 공개키를 VM에 넣어둔다"고 했는데, 정확히는 스터디장도 파일을 직접 넣지 않습니다. 이 일을 하는 것이 **cloud-init**입니다.

cloud-init은 거의 모든 클라우드용 리눅스 이미지에 내장된 초기화 도구로, **VM이 처음 부팅될 때** 실행되어 다음을 처리합니다:

- SSH 공개키를 `~/.ssh/authorized_keys`에 배치
- 호스트네임 설정, 파티션 확장
- 사용자가 지정한 초기화 스크립트(user-data) 실행

그럼 cloud-init은 그 공개키를 어디서 가져올까요? **메타데이터 서비스**입니다. 클라우드 플랫폼은 `http://169.254.169.254`라는 특수한 주소에서 "너는 누구고, 네 키는 이거고, 네 호스트네임은 이거다"라는 정보를 제공합니다. VM이 부팅되면 cloud-init이 이 주소에 접속해 자기 정보를 받아 갑니다.

```
VM 첫 부팅 → cloud-init 실행 → http://169.254.169.254 조회
           → 공개키·호스트네임 등 수신 → authorized_keys 배치 → SSH 접속 가능 상태
```

169.254.x.x는 링크-로컬 대역이라 외부로 라우팅되지 않는 주소인데, 하이퍼바이저/네트워크 계층이 이 요청을 가로채 메타데이터 서버로 보내줍니다. AWS에서도, 가비아에서도, 그리고 **여러분이 6회차에 배포할 OpenStack에서도** 똑같이 동작합니다 — OpenStack에서는 Neutron의 metadata agent가 이 가로채기를 담당하고, `docker ps`에서 `neutron_metadata_agent` 컨테이너로 확인할 수 있습니다.

이걸 알면 6회차에서 겪을 수 있는 상황 하나가 미리 설명됩니다: cirros 인스턴스가 부팅 로그에서 `169.254.169.254`에 접속을 시도하는 메시지를 볼 수 있는데, 그게 바로 인스턴스가 자기 키와 설정을 받으러 가는 장면입니다. 메타데이터 서비스가 죽어 있으면 인스턴스는 떴는데 SSH 키가 없어서 접속이 안 되는, "ACTIVE인데 못 들어가는" 상황이 생깁니다.

## B3. known_hosts와 서버 지문 — 첫 접속 질문의 정체

A4에서 첫 접속 때 `yes`를 입력했던 질문의 의미를 조금 더 파봅니다.

서버도 자기만의 키페어(호스트 키)를 갖고 있습니다. 첫 접속 시 서버가 자기 공개키의 요약값(지문, fingerprint)을 보여주고, 내가 `yes` 하면 그 지문이 `~/.ssh/known_hosts`에 저장됩니다. 다음 접속부터 SSH는 서버가 보내는 지문과 저장된 지문을 비교해서, **다르면 접속을 강하게 경고/거부합니다** (`REMOTE HOST IDENTIFICATION HAS CHANGED!`).

왜 이런 장치가 있냐면 — 누군가 중간에서 서버인 척하는 공격(중간자 공격)을 막기 위해서입니다. 다만 우리 스터디에서는 이 경고를 공격이 아닌 상황에서 만날 수 있습니다: **VM을 지우고 같은 IP로 새로 받으면**, 새 VM은 호스트 키가 다르므로 이 경고가 뜹니다. 그때는 `ssh-keygen -R <IP>`로 옛 지문을 지우고 다시 접속하면 됩니다. 경고의 의미를 알면 당황하지 않고, 모르면 "해킹당했나?" 하고 멈추게 되는 대표적인 지점입니다.
