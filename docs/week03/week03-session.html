도입 퀴즈 1/4 — 예습 질문. 답을 채팅에 한 줄로.

6단계 중 시간이 실제로 걸리는 구간은 어디고, 왜 그런가요?

5(준비물 수집) · 6(기동). 이미지를 네트워크로 받고 QEMU 프로세스를 띄우는 "실물" 작업이라 수십 초. 1~4는 인증·접수·배치·전달 같은 "결정"이라 수 초.

→ 인스턴스 생성이 느리면 의심할 곳은 5~6부터.

채팅 답 몇 개 읽어주고 열기. "5·6"만 맞으면 통과, 이유까지 말한 사람 한 명 지목해 부연.

도입 퀴즈 2/4

인스턴스가 대시보드에 보이는 시점과 실제로 존재하는 시점은 왜 다른가요? 몇 단계와 몇 단계 사이?

2단계(nova-api가 DB에 BUILD 기록)와 6단계(QEMU 기동, ACTIVE) 사이. nova-api는 접수하자마자 DB에 쓰고, 대시보드는 그 DB를 읽어 그리니까 아직 아무것도 안 만들어졌는데 보입니다.

→ "화면에 보이는 것"과 "실제로 존재하는 것"의 간극 — 클라우드 트러블슈팅의 출발점.

릴레이 정리 슬라이드의 관점 1번과 같은 얘기. 여기서 한 번 짚고 릴레이 뒤에 다시 연결.

도입 퀴즈 3/4

개인키와 공개키 중 서버에 저장되는 것은? 절대 남에게 전달하면 안 되는 것은?

서버에 저장되는 건 공개키(~/.ssh/authorized_keys). 절대 전달 금지는 개인키(.pem). 개인키 유출 = 그 서버 뚫린 것과 같음.

→ 오늘 DM으로 받은 .pem이 개인키. 단톡방·화면공유에 절대 노출 금지.

2부 화면공유 때 키 파일 내용이 터미널에 뜨지 않게 미리 경고. 리더 공개키가 같이 등록돼 있다는 것도 여기서 한 줄.

도입 퀴즈 4/4

Connection timed out과 Connection refused는 각각 무엇이 문제라는 신호인가요?

timed out = 길이 막힘. 패킷이 서버까지 못 감 — 방화벽·IP 오타·내 네트워크. refused = 도착했는데 문전박대. 서버까진 갔는데 22번 포트에서 거부 — sshd 미기동 등 서버 쪽.

→ 이 구분 하나로 트러블슈팅 방향이 절반으로 줄어듦. 오늘 2부에서 바로 씀.

오늘 SSH 타임아웃은 십중팔구 방화벽 소스 IP. 이 슬라이드 끝나면 바로 릴레이로.

릴레이 — 제가 한 명 지목하면, 그 단계에서 무슨 일이 일어나는지 한 문장. 막히면 다음 사람이 이어받기.

"인스턴스 생성" 버튼을 누르면, 안에서 무슨 일이 순서대로 일어날까요?

붉은 칸(5·6)이 시간이 실제로 걸리는 구간. 1~4는 "결정"이라 수 초, 5~6은 "실물 준비"라 수십 초 이상. 인스턴스 생성이 느리면 의심할 곳은 여기.

A를 누를 때마다 한 단계씩 열림(6번 뒤 한 번 더 누르면 정리 문장, 또 누르면 전부 닫힘). 지목한 사람이 말한 뒤에 그 단계를 열어 확인. 칸을 직접 클릭해도 열리고 닫힘. 4단계에서 conductor를 말하면 "예습자료엔 생략했지만 맞다, 2회차에 나온 그 부품"으로 받아주기. 틀려도 이름 부르지 않고 다음 사람에게 넘김.

릴레이 정리 — 여섯 단계에서 가져갈 관점 셋

  • 1빠른 구간과 느린 구간이 나뉜다. 1~4 결정(수 초), 5~6 실물(수십 초). 대시보드에 보이는 시점(2단계 BUILD)과 실제로 존재하는 시점(6단계 ACTIVE)의 간극이 트러블슈팅의 출발점.
  • 2모든 단계가 로그를 남긴다. 요청마다 req-로 시작하는 ID가 붙고, 여러 서비스 로그에 같은 ID가 찍힌다. 7회차 심화 미션이 이 ID로 6단계를 추적하는 것.
  • 3가비아도 같은 일을 했다. 오늘 여러분이 받은 VM을 만들 때 가비아 안에서도 본질적으로 같은 단계가 돌았다. 오늘 배운 건 OpenStack 지식이 아니라 클라우드가 동작하는 방식.

이 여섯 단계를 6회차에 여러분이 버튼으로 직접 실행하고, 7회차에 로그에서 흔적을 찾게 됩니다.

예습 질문 1·2가 여기서 답이 됨. 시간 없으면 3번만 말하고 넘어가기.

재료뜻우리가 쓸 값

오늘 여러분이 받은 가비아 VM에도 이 넷이 똑같이 있습니다 — Ubuntu 24.04 이미지, 2vCore/8GB 스펙, 개인키, 22·80·6080 방화벽.

"6단계 5번(Glance·Neutron)이 가져오는 게 Image와 Key Pair·Security Group"으로 앞 슬라이드와 연결. init.sh가 이미지·flavor·SG 규칙을 만들어둔다는 건 4회차에.

Kolla vs Kolla-Ansible — 한 장

KollaOpenStack 서비스들의 컨테이너 이미지. 2회차 docker ps의 28개가 이것

Kolla-Ansible그 이미지들을 배포·설정하는 도구. globals.yml · passwords.yml · inventory를 읽어 순서대로 띄움

설정 파일 셋은 전부 setup.sh가 자동 생성합니다. "스크립트가 뭘 대신해주는지"만 알면 됩니다 — 다음 주 4회차에 같이 실행.

여기서 버전(22.0.0 / 2026.1 Gazpacho) 얘기 꺼내지 않기 — 4회차 setup.sh 슬라이드에서. 1부 끝. 시계 확인: 22:25 넘었으면 바로 2부.

2부 — 배포받은 VM에 접속 체크포인트 1

미리 접속해 본 사람은 채팅에 ✅ 찍고, 화면 공유 보며 대기하거나 옆 사람 돕기.

# 키 파일 권한 먼저 (mac/Linux — Windows PowerShell은 이 줄 생략)
chmod 600 mykey.pem
ssh -i mykey.pem ubuntu@<공인IP>
메시지뜻조치
authenticity of host…이 서버 처음 보는데 믿을래?yes (예습 B3)
Permission denied (publickey)키 또는 계정명이 틀림-i 경로, 권한 600, 계정 ubuntu, DM 받은 키가 내 VM 것인지
Connection timed out길이 막힘 — 방화벽·IP카페/핫스팟이면 IP가 달라짐 → 리더에게 IP 추가 요청
Connection refused도착했는데 문전박대 — 서버 쪽부팅 직후면 잠시 대기

5분 룰. 타임아웃은 십중팔구 소스 IP — 가비아 콘솔에서 방화벽 규칙 추가는 내가 즉시. Permission denied는 Windows 파일 속성 → 보안 → 본인만 읽기. 키 분실은 리더 키로 들어가 새 공개키 주입.

2부 — VM 안에서 검증 + 기본 도구 체크포인트 2

lsb_release -a && nproc && free -h && df -h /   # 스펙 확인
ip a                                  # 사설 IP·인터페이스명
egrep -c '(vmx|svm)' /proc/cpuinfo    # 중첩 가상화 플래그
sudo apt update && sudo apt install -y git tmux
  • ·Ubuntu 24.04 · 2 vCPU · 7.x GB · 50GB — 8GB가 7.x로 찍히는 건 커널 예약분. 내 것만 작은 게 아닙니다
  • ·ip a에 공인 IP가 안 보이는 게 정상 — 가비아가 NAT로 붙여주는 구조. 6회차 Floating IP가 바로 이 개념
  • ·egrep 결과 1 이상 — 다음 슬라이드에서 전원 결과 모읍니다

apt upgrade는 여기서 돌리지 않는다 — 마무리에서 tmux에 걸어두기. 리더 공개키가 등록돼 있다는 것 한 줄 재안내, 원치 않으면 authorized_keys에서 삭제 가능.

결과 모으기 — egrep -c '(vmx|svm)' /proc/cpuinfo 숫자를 채팅에

0QEMU 에뮬레이션 모드 → 부팅 1~2분. 오늘 환경에선 나오면 안 되는 값 — 저에게 알려주세요

플래그가 있는 것과 커널 모듈이 올라오는 건 다른 얘기입니다. 모듈은 4회차 setup.sh가 처리합니다 — 오늘은 숫자 확인까지만.

프리런에서 KVM 부팅 확인됨. 가비아가 kvm_intel을 블랙리스트해서 setup.sh에 kvm-load.service를 넣은 얘기는 4회차에 — 오늘 꺼내면 길어짐. 0이 나오면 그 사람 VM 스펙 콘솔에서 확인.

마무리 — tmux 30초, 그리고 바로 실전

tmux new -s upgrade          # 세션 열기
sudo apt upgrade -y && echo DONE
# Ctrl+b, d  → 빠져나오기. SSH 끊어도 계속 돌아감
tmux attach -t upgrade       # 다음에 접속해서 결과 확인
  • 110명이 지금 동시에 upgrade를 돌리면 수 분씩 걸립니다. 세션 안에서 기다리지 않고 걸어두고 나가기.
  • 2커널이 올라갔다는 메시지가 보이면 sudo reboot 한 번. 4회차 전까지만 끝내면 됩니다.
  • 35회차 deploy는 이 tmux 안에서 밤새 돌아갑니다 — 오늘이 예행연습.

시간 남으면 "Ctrl+b, d"를 한 번씩 직접 해보게. 시간 없으면 명령 세 줄만 단톡방에 올리고 끝.

완료 기준 — 그리고 4회차

  • 1오늘 인증: SSH 접속 화면 + 검증 명령 출력 스크린샷을 단톡방에. upgrade 완료는 필수 아님
