왜 굳이 컨테이너일까

격리

OpenStack은 서비스가 수십 개고, 저마다 필요한 파이썬 라이브러리 버전이 다르다. 한 호스트에 다 깔면 서로 부딪힌다. 컨테이너면 각자 자기 방이 있다.

업그레이드

새 버전으로 올릴 때 패키지를 하나하나 갈지 않는다. 이미지 태그만 바꿔서 다시 띄우면 된다.

복구

서비스 하나가 꼬였으면 그 컨테이너만 지우고 다시 띄운다. 호스트는 건드리지 않는다.

Ansible에서 알아둘 건 세 개

인벤토리

어느 서버가 무슨 역할인지 적은 목록. control, network, compute… 우리는 VM 한 대가 전부 맡는다(all-in-one).

플레이북 · 롤

실제로 수행할 작업 묶음. Kolla-Ansible이 수백 개를 이미 다 짜뒀다. 우리가 새로 쓸 일은 없다.

멱등성

몇 번을 다시 돌려도 결과가 같다. 이미 된 건 건너뛰고, 안 된 것만 한다. 실패하면 그냥 다시 돌리면 된다.

그래서 우리가 만지는 파일은 딱 세 개

/etc/kolla/all-in-one

인벤토리. 모든 역할이 localhost 한 대로 되어 있다. 멀티노드면 여기 호스트만 늘어난다.

/etc/kolla/globals.yml

무엇을 켜고 끌지, 어느 NIC를 쓸지. Django로 치면 settings.py.

/etc/kolla/passwords.yml

DB, RabbitMQ, Keystone… 모든 서비스 비밀번호. 잃어버리면 복구 방법이 없다.

Kolla-Ansible은 컨테이너 안쪽만 책임진다.
호스트는 이미 준비돼 있다고 가정한다.
setup.sh는 그 가정을 만들어주는 스크립트다.

# 스크립트가 있는 폴더에서 file setup.sh # CRLF가 보이면 안 됨 chmod +x setup.sh ./setup.sh # 3~4분 뒤 READY ✅

① 호스트 전제 — 이름 해석, 시간, 메모리

127.0.1.1  study-vm
10.x.x.x   study-vm

우분투 기본값인 127.0.1.1 줄이 남아 있으면 RabbitMQ가 자기 이름을 루프백으로 해석해서, 루프백에만 귀를 연다. 다른 컨테이너는 전부 연결 거부.

/etc/hosts는 첫 번째로 맞는 줄이 이긴다. 그래서 밑에 한 줄 추가가 아니라, 그 줄 자체를 바꿔야 한다.

chrony: 토큰에 시각이 박혀서, 시계가 틀리면 인증이 깨진다. 스왑 8GB: deploy 순간 피크에 OOM으로 죽지 않게.

내 VM에서 확인

cat /etc/hosts swapon --show chronyc tracking | head -3

② 커널 파라미터 — 패킷을 넘겨주고, 버리지 않게

ip_forward=1 — 호스트가 인스턴스와 바깥 사이에서 라우터 노릇을 하려면 커널이 패킷을 넘겨줘야 한다. 원래 도커가 켜주는데, Kolla가 도커 쪽을 꺼두기 때문에 우리가 직접 켠다.

rp_filter=2 — 들어온 길과 나갈 길이 다른 패킷을 버리는 기능. 우리 구조는 길이 비대칭이라 strict(1)이면 FIP 응답이 로그 한 줄 없이 사라진다. loose(2)로.

7회차 트러블슈팅에서 다시 만납니다. "핑은 안 가는데 에러가 아무 데도 없다."

내 VM에서 확인

sysctl net.ipv4.ip_forward \ net.ipv4.conf.all.rp_filter cat /etc/sysctl.d/99-kolla.conf

③ veth — 외부망 NIC이 없으니 가짜 랜선을

Kolla는 외부망 NIC으로 IP 없는 빈 NIC을 요구한다. 배포 때 OVS가 통째로 가져가니까. eth0을 주면 그 순간 SSH가 끊긴다.

veth0을 브리지에 물리면 플러딩이 밖으로 샌다. SU Cloud 운영계에서 실제로 난 장애. UP만 시켜두고 끝.

내 VM에서 확인

ip -br link systemctl cat veth-setup

내 VM에서 확인 — 주석 빼고 실제 값만

grep -v '^#' \ /etc/kolla/globals.yml \ | grep -v '^$'

openstack_release는 일부러 안 적었다. 22.0.0 기본값이 정답이고, 잘못 적으면 pull이 실패한다.

prechecks — 우리가 만든 전제를 Kolla가 검사한다

VIP가 실제 인터페이스에 있나 · 필요한 포트가 비어 있나 · 두 NIC이 존재하고 UP인가 · Docker와 의존성은 맞나. 결국 setup.sh 전체가 prechecks를 통과시키기 위한 작업 목록이다.

--use-test-images는 prechecks에만 있는 옵션. pull이나 deploy에 붙이면 unrecognized arguments로 바로 죽는다.

그리고 bootstrap-servers는 우리 계정을 docker 그룹에 넣는 걸 빠뜨린다. setup.sh가 대신 넣었지만, 그룹은 새로 로그인해야 반영된다.

내 VM에서 확인

ls /etc/kolla ls ~/kolla-backup id | tr ',' '\n' | grep docker
