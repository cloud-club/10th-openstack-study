deploy 데이

치는 명령은 세 줄. 나머지는 기다리면서 구경합니다.
deploy는 세션 안에 안 끝나고, 그게 정상입니다.

source activate
kolla-ansible pull
kolla-ansible deploy

4회차, 9/21

setup.sh로 prechecks까지

Docker 엔진은 돌고 있지만 컨테이너는 0개. 이미지도 아직 없음.

5회차, 오늘

pull, 그리고 deploy

pull은 이미지만 받는다. deploy가 그 이미지로 컨테이너를 만들고 띄운다.

6회차, 10/6(화)

post-deploy와 init.sh

접속 정보 파일을 만들고, 네트워크와 이미지를 준비해서 cirros에 SSH까지.

지난주 끝에 docker ps는 헤더만 있는 빈 표였습니다. 오늘 끝나면 여기가 수십 줄로 채워집니다.

시작 전에 네 가지만

  • READY ✅ 인증을 했는지. 미인증자는 오늘 deploy 대신 7회차 구제 트랙으로 갑니다.
  • docker 그룹이 잡혀 있는지. 안 보이면 exit 후 SSH 재접속.
  • docker ps가 sudo 없이 되고, 빈 표가 나오면 정상.
  • tmux가 있는지. setup.sh가 설치해 두었지만, 없으면 sudo apt install -y tmux.
$ id | grep -o docker
docker          ← 이 줄이 떠야 함

$ docker ps
CONTAINER ID   IMAGE   ...  ← 헤더만

$ tmux -V
tmux 3.x        ← 버전이 뜨면 OK

그룹이 안 잡힌 세션에서 돌리면 pull이나 deploy 도중에 permission denied로 죽습니다. 여기서 걸러내세요.

첫 번째 줄: tmux 열고 venv 켜기

$ tmux new -s kolla
$ source ~/kolla-venv/bin/activate
(kolla-venv) $   ← 이렇게 바뀌면 OK

tmux는 오늘의 생명줄입니다. SSH가 끊겨도 tmux 안에서 돌린 작업은 서버에서 계속 돌아갑니다.

venv는 setup.sh가 kolla-ansible을 설치해 둔 파이썬 환경입니다. 켜지 않으면 kolla-ansible: command not found가 뜹니다.

체크포인트 1

두 번째 줄: 이미지 미리 받기

(kolla-venv) $ kolla-ansible pull -i /etc/kolla/all-in-one
...
PLAY RECAP *********************************
localhost : ok=..  changed=..  failed=0   ← 통과

왜 pull을 따로 하나. deploy 도중에 이미지를 받다가 네트워크가 튀면 배포가 중간에 죽습니다. 미리 받아두면 deploy가 안정적입니다.

타임아웃이 나면 같은 명령을 다시 치면 됩니다. 이미 받은 이미지는 건너뜁니다.

pull 도는 동안: 이미지와 컨테이너는 다르다

예습 답 맞추기. 컨테이너와 VM의 차이를 한 문장으로, 돌아가면서 발표.

실물 확인. tmux 새 창에서 두 명령을 번갈아 쳐 봅니다.

이미지는 계속 늘어나는데 컨테이너는 0개. pull은 설계도만 받는 단계입니다.

# 창 전환: Ctrl+b 누른 뒤 n

$ docker images | wc -l
  → 계속 늘어남

$ docker ps
  → 여전히 빈 표

하나로 못 합치는 이유: init.sh가 쓰는 세 가지는 deploy 전에는 아직 없습니다.

br-exopenvswitch 컨테이너가 뜨면서 만든다
admin-openrc.shpost-deploy가 만든다
openstack 명령keystone, neutron 컨테이너가 떠야 대답한다
[1/4] deploy 확인 + post-deploy

먼저 deploy가 진짜 끝났는지 본다

# 핵심 컨테이너 다섯 개가 없으면 즉시 중단
for c in nova_compute neutron_server \
         neutron_l3_agent openvswitch_vswitchd keystone
  docker ps ... | grep -qx "$c" || die

ip link show br-ex || die   # br-ex도 확인

# 접속 정보 파일이 없을 때만
kolla-ansible post-deploy -i /etc/kolla/all-in-one

deploy가 덜 끝났으면 엉뚱한 곳에서 죽지 않고 여기서 이유를 말하고 멈춥니다.

post-deploy는 /etc/kolla/admin-openrc.sh를 만듭니다. keystone 주소와 admin 계정이 들어 있고, 이걸 source해야 openstack 명령이 인증됩니다.

[2/4] br-ex-gw.service

호스트가 가짜 외부망의 게이트웨이가 된다

필요한 것
Floating IP가 속할 외부 네트워크와, 그 네트워크의 게이트웨이.
우리 환경
가비아 VM에는 그런 외부망이 없다. 그래서 호스트 안에 192.168.200.0/24를 만들고 호스트가 직접 게이트웨이를 맡는다.
init.sh가 한 일
br-ex에 192.168.200.1 부여, 이 대역에서 나가는 패킷을 eth0 주소로 바꾸는 MASQUERADE, FORWARD ACCEPT. 전부 systemd 유닛이라 재부팅에도 살아남는다.
안 하면
인스턴스는 떠도 인터넷에 못 나가고, 호스트에서 FIP로 ping이 안 간다.

왜 setup.sh에서 안 했나: 그때는 br-ex가 없어서 IP를 붙일 대상이 없다. 그래서 유닛도 br-ex가 생길 때까지 최대 2분 기다린다. (SU Cloud 함정 7)

끝나면 INIT ✅와 Horizon 접속 정보가 뜹니다. 이 화면이 6회차 인증입니다.

exists network provider_network \
  || openstack network create ...

# iptables: -C로 확인, 없을 때만 -A
iptables -t nat -C POSTROUTING ... \
  || iptables -t nat -A POSTROUTING ...

# IP: grep으로 확인
ip addr show dev br-ex | grep -q .1/ \
  || ip addr add 192.168.200.1/24 dev br-ex

세 번째 줄: 본 배포

(kolla-venv) $ kolla-ansible deploy -i /etc/kolla/all-in-one

플래그 없이 칩니다. --use-test-images는 prechecks 전용이라 deploy에 붙이면 unrecognized arguments로 바로 죽습니다. 지난주 명령을 보고 따라 치지 마세요.

  • 30~60분 걸립니다. 세션 안에 안 끝나는 게 정상입니다.
  • 초반 5분, 빨간 fatal 없이 로그가 흐르는지만 전원 확인합니다.
