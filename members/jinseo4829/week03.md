# Week 03 - 인스턴스 생성 과정과 SSH

## 1. 이번 주에 배우는 내용

이번 주에는 클라우드에서 인스턴스 생성 버튼을 눌렀을 때 내부에서 어떤 작업이 일어나는지 알아보고, 실제로 지급받은 가비아 VM에 SSH로 접속해 서버 상태를 확인한다.

2회차에는 OpenStack을 구성하는 서비스들의 역할을 배웠다면, 3회차에는 그 서비스들이 인스턴스 하나를 만들기 위해 어떤 순서로 협력하는지 살펴본다.

## 2. 인스턴스 생성 6단계

```text
1. 인증       Horizon/CLI → Keystone에서 토큰 발급
2. 접수       nova-api가 요청을 받고 DB에 BUILD 상태로 기록
3. 배치 결정  scheduler가 Placement를 조회해 실행 노드 선택
4. 작업 전달  nova-compute가 RabbitMQ를 통해 작업 수신
5. 준비       Glance 이미지, Neutron 포트와 IP, 필요 시 Cinder 볼륨 준비
6. 기동       libvirt가 QEMU를 실행하고 상태가 ACTIVE로 변경
```

### 1단계: 인증

사용자가 ID와 비밀번호 등의 인증 정보를 Keystone에 보내면 토큰을 발급받는다. 이후 Nova 같은 다른 서비스에 API 요청을 보낼 때 `X-Auth-Token` 헤더에 이 토큰을 넣는다.

토큰에는 요청한 사용자가 누구인지, 어느 프로젝트에 속하는지, 어떤 권한을 가졌는지에 관한 정보가 담긴다.

### 2단계: 요청 접수

nova-api가 요청을 받으면 토큰과 요청 형식을 확인한다. 어떤 이미지와 크기, 네트워크를 사용할지 검사한 뒤 DB에 인스턴스 레코드를 만들고 상태를 `BUILD`로 기록한다.

이 시점부터 Horizon 화면에 인스턴스가 표시되지만 실제 VM 프로세스는 아직 없다. 대시보드는 DB에 기록된 상태를 보여주기 때문이다.

### 3단계: 배치 결정

nova-scheduler는 VM을 어느 컴퓨트 노드에서 실행할지 결정한다.

1. Placement에서 각 노드의 남은 vCPU, 메모리, 디스크를 확인한다.
2. Filter 단계에서 조건을 만족하지 못하는 노드를 제외한다.
3. Weigh 단계에서 남은 후보에 점수를 매긴다.
4. 가장 적합한 컴퓨트 노드를 선택한다.

all-in-one 환경에서는 선택할 노드가 한 대뿐이지만, 실제로는 같은 절차를 거친다.

### 4단계: 작업 전달

선택된 노드의 nova-compute가 RabbitMQ를 통해 VM 생성 작업을 받는다. 오래 걸리는 작업이므로 요청을 보낸 쪽이 완료될 때까지 기다리지 않는 비동기 `cast` 방식을 사용한다.

### 5단계: 부팅에 필요한 것 준비

nova-compute는 VM 실행에 필요한 자원을 다른 서비스에 요청한다.

- **Glance**: 부팅 이미지를 제공한다. 처음 사용하는 이미지는 내려받아야 하지만 이후에는 로컬 캐시를 사용할 수 있다.
- **Neutron**: 가상 포트를 만들고 MAC 주소와 IP를 할당한다.
- **Cinder**: 별도 블록 볼륨이 필요한 경우 볼륨을 연결한다.

네트워크 전송과 실제 자원 준비가 필요하기 때문에 앞 단계보다 오래 걸린다.

### 6단계: VM 기동

준비가 끝나면 nova-compute가 libvirt에 VM 정의를 전달한다. libvirt는 XML 형식의 정의를 이용해 QEMU 프로세스를 실행한다. VM 생성이 완료되면 인스턴스 상태가 `BUILD`에서 `ACTIVE`로 바뀐다.

`ACTIVE`는 하이퍼바이저에서 VM이 실행됐다는 뜻이다. 게스트 운영체제 부팅과 SSH 준비까지 끝났다는 뜻은 아니므로, 상태가 `ACTIVE`여도 잠시 동안 SSH가 연결되지 않을 수 있다.

## 3. 빠른 단계와 느린 단계

1단계부터 4단계까지는 인증, 기록, 계산, 명령 전달이 중심이라 비교적 빠르다. 5단계와 6단계에서는 이미지 전송, 네트워크 생성, 디스크 준비, QEMU 프로세스 실행처럼 실제 자원을 다루기 때문에 시간이 더 걸린다.

인스턴스 생성이 느릴 때는 현재 상태가 어디에서 멈췄는지 먼저 확인해야 한다.

- `scheduling`: 실행할 노드를 고르는 중
- `networking`: Neutron이 네트워크를 준비하는 중
- `spawning`: QEMU로 VM을 실행하는 중
- `ACTIVE`: VM 프로세스 실행 완료
- `ERROR`: 생성 과정 중 오류 발생

모든 요청에는 `req-`로 시작하는 request-id가 붙는다. 같은 request-id를 Nova, Neutron 등 여러 서비스의 로그에서 찾으면 하나의 요청이 어느 단계에서 실패했는지 추적할 수 있다.

### No valid host was found

이 오류는 scheduler가 조건에 맞는 컴퓨트 노드를 찾지 못했다는 의미다. 모든 노드가 Filter 단계에서 제외된 것이므로 메모리, vCPU, 디스크 등의 자원이 부족하지 않은지 확인해야 한다.

## 4. SSH와 키페어

SSH는 원격 서버의 터미널을 암호화된 통신으로 사용할 수 있게 해 주는 프로토콜이며 기본 포트는 22번이다.

클라우드 VM은 일반적으로 비밀번호 대신 키페어 인증을 사용한다.

- **공개키**: 서버의 `~/.ssh/authorized_keys`에 저장한다.
- **개인키**: 사용자 컴퓨터에만 보관한다. 실습에서 받은 `.pem` 파일이 개인키다.

서버는 접속자가 등록된 공개키와 짝을 이루는 개인키를 가지고 있는지 확인한다. 개인키 자체를 서버로 보내는 방식이 아니기 때문에 비밀번호 인증보다 안전하다.

개인키가 유출되면 다른 사람이 서버에 접속할 수 있으므로 메신저, GitHub, 공개 저장소 등에 올리면 안 된다.

## 5. SSH 접속 방법

macOS와 Linux에서는 먼저 개인키 파일의 권한을 제한한다.

```bash
chmod 600 ~/Downloads/mykey.pem
```

`600`은 파일 소유자만 읽고 쓸 수 있고 다른 사용자는 접근할 수 없다는 뜻이다. 권한이 너무 열려 있으면 SSH는 `UNPROTECTED PRIVATE KEY FILE` 경고와 함께 키 사용을 거부한다.

접속할 때는 키 파일의 실제 경로와 Ubuntu 기본 계정을 지정한다.

```bash
ssh -i ~/Downloads/mykey.pem ubuntu@<공인IP>
```

`-i`는 인증에 사용할 개인키 파일을 지정하는 옵션이다. 키가 Downloads 폴더에 있는데 `-i mykey.pem`만 입력하면 현재 디렉터리에서 파일을 찾기 때문에 `Identity file not accessible` 오류가 발생할 수 있다. 이 경우 SSH가 키를 사용하지 못하고 비밀번호 인증을 시도할 수도 있다.

첫 접속에서는 서버를 신뢰할 것인지 묻는다. 서버 지문을 확인하고 `yes`를 입력하면 해당 지문이 `~/.ssh/known_hosts`에 저장된다.

## 6. 접속 후 서버 확인

| 명령어 | 확인할 내용 |
| --- | --- |
| `lsb_release -a` | Ubuntu 버전 |
| `nproc` | vCPU 개수 |
| `free -h` | 메모리 사용량 |
| `df -h /` | 루트 파일시스템의 전체, 사용, 남은 용량 |
| `ip a` | 네트워크 인터페이스와 IP 주소 |

중첩 가상화 지원 여부는 다음 명령으로 확인한다.

```bash
egrep -c '(vmx|svm)' /proc/cpuinfo
```

중첩 가상화 확인 결과가 1 이상이면 VM 안에서 KVM 하드웨어 가속을 사용할 수 있다. 결과가 0이면 하드웨어 가상화 기능이 내부 VM에 노출되지 않은 것이므로 OpenStack 인스턴스는 QEMU 소프트웨어 에뮬레이션을 사용해야 한다.

## 7. SSH 오류 구분

| 오류 | 의미 | 먼저 확인할 것 |
| --- | --- | --- |
| `Permission denied (publickey)` | 공개키와 개인키가 맞지 않거나 계정명이 틀림 | 키 경로와 `ubuntu` 계정 확인 |
| `UNPROTECTED PRIVATE KEY FILE` | 개인키 권한이 너무 열려 있음 | `chmod 600` 적용 |
| `Identity file not accessible` | 지정한 개인키 파일을 찾을 수 없음 | `-i` 뒤의 전체 경로 확인 |
| `Connection timed out` | 패킷이 서버의 SSH 포트까지 도달하지 못함 | 공인 IP, 방화벽, 22번 포트, 현재 네트워크 확인 |
| `Connection refused` | 서버에는 도달했지만 22번 포트에서 연결을 받지 않음 | 서버 부팅 상태와 SSH 서비스 확인 |

`timed out`은 서버까지 가는 길이 막힌 경우이고, `refused`는 서버까지 도착했지만 SSH 서비스를 이용할 수 없는 경우다. 둘을 구분하면 클라이언트와 네트워크를 먼저 볼지, 서버 내부를 먼저 볼지 판단할 수 있다.

## 8. cloud-init과 메타데이터 서비스

클라우드 VM 이미지에는 첫 부팅 때 초기 설정을 수행하는 cloud-init이 들어 있다.

cloud-init은 다음과 같은 작업을 한다.

- SSH 공개키를 `~/.ssh/authorized_keys`에 저장
- 호스트네임 설정
- 디스크 파티션 확장
- user-data에 작성한 초기화 스크립트 실행

cloud-init은 `http://169.254.169.254`에 있는 메타데이터 서비스에서 VM에 필요한 정보를 받아 온다.

```text
VM 첫 부팅
  → cloud-init 실행
  → 169.254.169.254에서 메타데이터 조회
  → 공개키와 호스트네임 등 수신
  → authorized_keys에 공개키 저장
  → SSH 접속 준비 완료
```

`169.254.169.254`는 외부로 라우팅되지 않는 링크 로컬 주소다. OpenStack에서는 Neutron metadata agent가 이 주소로 들어오는 요청을 메타데이터 서비스에 전달한다.

메타데이터 서비스에 문제가 생기면 하이퍼바이저에서 VM이 실행되어 `ACTIVE`로 보이더라도 공개키가 등록되지 않아 SSH에 실패할 수 있다.

## 9. known_hosts와 서버 지문

클라이언트만 키페어를 사용하는 것이 아니라 SSH 서버도 호스트 키를 가지고 있다. 첫 접속 때 보이는 fingerprint는 서버 공개키의 요약값이다.

한 번 저장한 서버의 지문이 다음 접속에서 달라지면 SSH는 `REMOTE HOST IDENTIFICATION HAS CHANGED!` 경고를 표시한다. 이는 접속 중간에서 다른 서버가 가로채는 공격을 방지하기 위한 기능이다.

실습에서는 VM을 삭제한 뒤 같은 IP로 새 VM을 발급받았을 때도 이 경고가 나타날 수 있다. 새 VM은 이전 VM과 다른 호스트 키를 사용하기 때문이다. 재발급된 서버가 맞는지 확인한 뒤 다음 명령으로 기존 지문을 삭제할 수 있다.

```bash
ssh-keygen -R <공인IP>
```

## 10. 이번 주에 이해한 핵심

- 대시보드에 인스턴스가 보이는 것과 실제 VM 프로세스가 만들어진 것은 같은 시점이 아니다.
- 인스턴스 생성은 인증, 접수, 배치, 작업 전달, 자원 준비, 기동 순서로 진행된다.
- `ACTIVE` 상태여도 게스트 운영체제와 SSH 준비가 끝나지 않았을 수 있다.
- SSH 공개키는 서버에 저장하고 개인키는 사용자만 보관한다.
- SSH 오류 문구를 구분하면 문제를 찾아볼 위치를 좁힐 수 있다.
- cloud-init은 메타데이터 서비스에서 공개키 등의 초기 정보를 받아 VM에 적용한다.

## 11. 예습 질문 답변

### 1. 인스턴스 생성 6단계 중 시간이 실제로 걸리는 구간은 어디고, 왜 그런가요?

5단계와 6단계에서 시간이 많이 걸린다. 1단계부터 4단계까지는 인증, DB 기록, 노드 선택, 메시지 전달처럼 주로 정보를 처리하는 작업이다. 반면 5단계에서는 Glance 이미지 다운로드, Neutron 포트와 IP 생성, Cinder 볼륨 연결이 필요하고, 6단계에서는 libvirt가 QEMU 프로세스를 실행해 실제 VM을 기동하므로 시간이 더 오래 걸린다.

### 2. 인스턴스가 대시보드에 보이는 시점과 실제로 존재하는 시점은 왜 다른가요?

2단계에서 nova-api가 DB에 인스턴스 레코드를 만들고 `BUILD` 상태로 기록하면 Horizon은 그 DB 상태를 보고 인스턴스를 표시한다. 하지만 실제 VM 프로세스는 5단계에서 필요한 자원을 준비한 뒤 6단계에서 QEMU가 실행되어야 만들어진다. 따라서 2단계와 6단계 사이에는 화면에는 보이지만 실제 VM은 아직 준비 중인 시간이 존재한다.

### 3. 개인키와 공개키 중 서버에 저장되는 것은 무엇이고, 절대 남에게 전달하면 안 되는 것은 무엇인가요?

서버의 `~/.ssh/authorized_keys`에는 공개키가 저장된다. `.pem` 형태의 개인키는 사용자 컴퓨터에만 보관해야 하며 절대 다른 사람에게 전달하거나 공개 저장소에 올리면 안 된다.

### 4. Connection timed out과 Connection refused는 각각 무엇이 문제라는 신호인가요?

`Connection timed out`은 패킷이 서버의 SSH 포트까지 도달하지 못했다는 뜻이므로 IP 주소, 방화벽, 22번 포트 허용 여부, 현재 네트워크를 확인해야 한다. `Connection refused`는 서버에는 도착했지만 22번 포트에서 연결을 받지 않았다는 뜻이므로 서버의 부팅 상태와 SSH 서비스 실행 여부를 확인해야 한다.

## 12. 메타데이터 서비스 추가 정리

### 링크 로컬 주소란?

`169.254.0.0/16`은 현재 연결된 로컬 네트워크 안에서만 사용하는 주소 대역이다. 일반 IP와 달리 라우터를 거쳐 인터넷이나 다른 네트워크로 전달되지 않는다.

클라우드에서는 이 대역에 속하는 `169.254.169.254`를 메타데이터 조회용 주소로 사용한다. 이 주소로 보낸 요청이 로컬 가상 네트워크 안에서 처리된다는 뜻이다.

### VM이 메타데이터를 받는 과정

VM 옆에 `169.254.169.254`라는 실제 서버가 따로 있는 것은 아니다. VM이 이 주소로 요청하면 Neutron이 요청을 메타데이터 프록시에 연결하고, 프록시가 Nova metadata API에 대신 정보를 요청한다.

```text
VM의 cloud-init
  → 169.254.169.254로 요청
  → Neutron 가상 네트워크가 메타데이터 프록시로 연결
  → 프록시가 Nova metadata API에 별도의 요청 전송
  → Nova가 해당 VM의 공개키, 호스트네임, user-data 등을 반환
  → 프록시가 응답을 VM에 전달
  → cloud-init이 받은 정보를 VM에 적용
```

실제 통신은 다음 두 구간으로 나누어 생각할 수 있다.

```text
1. VM → 로컬 Neutron 메타데이터 프록시
2. 메타데이터 프록시 → Nova metadata API
```

VM이 보낸 링크 로컬 패킷 자체가 외부의 Nova 서버까지 이동하는 것은 아니다. Neutron 프록시가 관리 네트워크를 통해 Nova에 새로운 요청을 보내고, 받은 답을 원래 VM에 돌려준다.

### Neutron 네트워크 계층에서 처리하는 이유

Neutron은 가상 포트와 인스턴스의 관계를 알고 있다.

- 요청이 들어온 가상 포트
- 포트에 연결된 인스턴스
- 포트의 IP와 MAC 주소
- 인스턴스가 속한 네트워크와 프로젝트

이 정보를 이용하면 VM이 자신의 인스턴스 ID를 직접 주장하지 않아도, Neutron이 어떤 VM의 요청인지 식별해 해당 VM의 메타데이터만 전달할 수 있다.

네트워크 계층에서 처리할 때 얻는 장점은 다음과 같다.

1. **보안**: VM이 다른 인스턴스의 정보를 요청하는 것을 막을 수 있다.
2. **격리**: 모든 VM이 같은 `169.254.169.254`를 사용해도 각 가상 네트워크 안에서 자기 정보만 받을 수 있다.
3. **초기 부팅 지원**: DNS와 외부 네트워크가 준비되지 않은 시점에도 고정된 주소로 초기 정보를 받을 수 있다.
4. **관리망 보호**: Nova의 실제 관리 API 주소와 인증 정보를 VM에 직접 노출하지 않아도 된다.

OpenStack에서는 KVM이나 QEMU가 이 요청을 직접 처리하기보다는 Neutron의 가상 네트워크, 메타데이터 프록시, metadata agent가 주로 처리한다. Kolla-Ansible로 배포한 환경에서는 `neutron_metadata_agent` 컨테이너로 확인할 수 있다.
