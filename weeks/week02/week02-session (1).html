채팅 퀴즈 1/3 — 답은 채팅에 한 줄로. 정답보다 지금 머릿속에 있는 것 그대로.

Nova / Neutron / Glance / Keystone을 AWS의 EC2 / VPC / AMI / IAM과 짝지어 보세요.

그리고 — 넷 중에 Keystone만 "모든 요청의 관문"이라 부르는 이유는?

Nova = EC2 · Neutron = VPC · Glance = AMI · Keystone = IAM

  • 1클라이언트 → Keystone(:5000)에 ID/비밀번호
  • 2Keystone → 토큰 + 서비스 카탈로그
  • 3클라이언트 → nova-api(:8774), X-Auth-Token 첨부
  • 4nova-api → Keystone에 "이 토큰 유효해?"
  • 5유효하면 처리

어느 서비스를 부르든 4단계에서 반드시 Keystone을 거친다. 그래서 관문.

보강: Fernet은 DB 저장 없이 대칭키 복호화로 검증(stateless). 카탈로그 덕에 클라이언트는 Keystone 주소 하나만 알면 됨. 포트 5000/8774를 방화벽에서 안 여는 이유 → Horizon이 VM 안에서 대신 호출.

채팅 퀴즈 2/3 — 하나만 생각나면 하나만.

nova-api와 nova-compute는 왜 REST가 아니라 메시지 큐(RabbitMQ)로 통신할까요?

이유 3가지.

  • 1비동기 — VM 생성은 수십 초~수 분. 던지고(cast) 바로 다음 요청. 버튼 누르자마자 BUILD로 보이는 이유
  • 2내결함성 — compute가 죽어도 메시지는 큐에 남았다가 복구 후 처리
  • 3수평 확장 — 같은 큐를 구독하는 compute를 늘리면 자동 분산

기준 한 줄: 서비스 간은 REST, 서비스 내부는 MQ.

보강: conductor가 왜 있나 → compute가 DB에 직접 못 붙게 중계(보안 + 업그레이드 격리). "RabbitMQ 죽으면?"은 3번으로 넘기기.

채팅 퀴즈 3/3 — 이건 다같이 추측.

docker ps에 뜨는 mariadb · rabbitmq · memcached는 OpenStack 프로젝트가 아닙니다. 각각 무슨 역할이고, 하나가 죽으면 무슨 일이 벌어질까요?

컨테이너역할죽으면
mariadb전 서비스의 영속 데이터. "VM이 몇 개고 상태가 뭔지" 전부전체 마비. API가 읽고 쓸 수 없음
rabbitmq서비스 내부 RPC 버스API는 응답하지만 실행이 안 됨. BUILD에서 영원히
memcached토큰 검증 결과 캐싱느려지지만 동작함

연결: 1회차 OOM 사례 — 6GB VM에서 첫 희생자가 mysqld. 이 표 기준으로 최악의 희생자. 오늘 오후 프리런 `docker ps` 28개에 이 셋이 실제로 있음, haproxy는 AIO라 꺼서 없음.

  • 2모든 요청은 Keystone을 거치고(REST), 서비스 안에서는 RabbitMQ로 흐르고(MQ), 상태는 전부 MariaDB에.

오늘 배운 부품들이 버튼 하나에 어떻게 협동하는지

  • A2인스턴스 생성 6단계 — 인증 → 접수(BUILD) → 배치 결정(Placement·Filter/Weigh) → 작업 수신(RabbitMQ cast) → 준비물 수집(Glance·Neutron·Cinder) → 기동(libvirt→QEMU, ACTIVE). Keystone·nova-api·scheduler·conductor·compute가 전부 순서대로 등장
  • A3SSH 키페어의 원리 — 공개키는 자물쇠(서버), 개인키는 열쇠(내 노트북). 왜 비밀번호보다 안전한지, 왜 개인키를 단톡방에 올리면 안 되는지
  • B심화(선택) — BUILD→ACTIVE→ERROR 상태 전이, No valid host was found의 의미, cloud-init과 169.254.169.254 메타데이터 서비스, known_hosts와 서버 지문
