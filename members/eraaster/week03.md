클라우드 콘솔(가비아, AWS, 혹은 OpenStack Horizon)에서 **[인스턴스 생성]** 버튼을 누르면 단 몇십 초 만에 IP가 할당된 서버가 등장합니다. 사용자에게는 마법 같은 클릭 한 번이지만, 그 뒤에서는 거대한 분산 시스템이 바쁘게 움직입니다.
오늘은 그 몇십 초 동안 내부에서 일어나는 **6단계의 오케스트레이션 과정**과, 생성된 인스턴스에 안전하게 접근하기 위한 **SSH의 동작 원리**를 상세히 파헤쳐 보겠습니다.

### 🏗️ 1. "인스턴스 생성" 버튼 뒤의 6단계 프로세스
OpenStack을 기준으로 살펴보면, 인스턴스 생성 시 핵심 컴포넌트들(Keystone, nova-api, scheduler, compute, Glance, Neutron, libvirt)이 유기적으로 통신하며 자원을 프로비저닝합니다.
전체적인 흐름은 다음과 같습니다.
```
1. 인증 (Keystone) ➔ 2. 접수 (nova-api) ➔ 3. 배치 결정 (scheduler) ➔ 
4. 작업 수신 (nova-compute) ➔ 5. 준비물 수집 (Glance, Neutron) ➔ 6. 기동 (libvirt/QEMU)
```

#### 1단계 : 인증 (수 초 미만)
모든 API 요청의 첫 관문은 **Keystone**입니다. 사용자 크리덴셜(ID/PW)을 통해 토큰을 발급받습니다. 이후 모든 API 호출에는 HTTP 헤더에 X-Auth-Token 형태로 이 토큰이 첨부됩니다.
이 토큰 안에는 "누가, 어느 프로젝트에서, 어떤 권한으로 요청했는지"가 암호화되어 담겨 있습니다.

#### 2단계 : 접수 (수 초 미만)
**nova-api**가 요청을 받습니다. 토큰을 검증하고, 유저가 요구한 스펙(어떤 이밎, CPU/RAM 크기, 어느 네트워크 등)의 형식을 확인합니다.
> 🚨 주의 깊게 볼 점 :
nova-api는 요청이 타당하다면 **곧바로 DB에 인스턴스 레코드를 만들고 상태를 BUILD로 기록**합니다. 놀랍게도 이 순간부터 대시보드 화면에 인스턴스가 나타납니다. 아직 하이퍼바이저에는 아무것도 만들어지지 않았는데 말이죠 !
여기서 **"화면에 보이는 것"과 "실제로 존재하는 것"의 간극**이 처음 발생하며, 이는 클라우드 트러블슈팅의 중요한 출발점이 됩니다.

#### 3단계 : 배치 결정 (수 초)
이제 **nova-scheduler**가 "이 VM을 어느 물리 서버에 배치할까?"를 계산합니다.
1. **조회** : Placement API를 통해 각 노드의 잔여 자원(vCPU, 메모리, 디스크)을 확인합니다.
2. **Filter** : 조건에 맞지 않는 물리 노드를 탈락시킵니다. (예 : 요구 메모리보다 남은 메모리가 적은 노드)
3. **Weigh** : 살아남은 후보 노드들에게 가중치 점수를 매겨 최종 1대를 낙점합니다.

#### 4단계 : 작업 수신 (즉시)
결정이 내려지면 해당 노드의 **nova-compute**에게 메시지 큐(RabbitMQ)를 통해 작업이 전달됩니다. 이때 중요한 것은 **비동기(cast) 방식**으로 던진다는 것입니다. 큐에 미시지를 던져놓고 끝날 때까지 기다리지 않기 때문에, nova-api는 병목 없이 즉각적으로 다음 사용자의 요청을 처리할 수 있습니다.

#### 5단계 : 준비물 수집 (수십 초)
nova-computer가 본격적으로 행동에 나서며 세 곳에 자원을 요청합니다. **(실제로 가장 시간이 오래 걸리는 구간 1)
- **Glance (이미지)** : 부팅할 OS 이미지를 다운로드합니다. (최초 다운로드는 네트워크를 타서 오래 걸리지만, 로컬 노드에 캐시된 이후부터는 매우 빠릅니다.)
- **Neutron (네트워크)** : "가상 포트 하나 만들어 줘"라고 요청하여, MAC 주소와 IP가 할당된 가상 NIC 인터페이스를 바인딩합니다.
- **Cinder (스토리지)** : 별도의 블록 스토리지를 마운트하는 경우에만 호출됩니다.

#### 6단계 : 기동 (수십 초)
준비물이 모두 모이면 nova-compute가 **libvirt**에게 VM의 스펙이 담긴 정의서(XML)를 넘깁니다. 이를 바탕으로 물리 서버에서 **QEMU/KVM 프로세스**가 실행됩니다. **(시간이 걸리는 구간 2)
- 인스턴스의 상태가 BUILD에서 ACTIVE로 바뀌면 OpenStack 시스템 관점에서는 생성이 완료된 것입니다.
- 단, 게스트 OS 부팅 시간은 별도입니다. ACTIVE 상태가 되었더라도 SSH 접속이 가능해지려면 내부 Linux가 부팅될 때까지 약간의 추가 시간이 필요합니다.

### 🔐 2. SSH 접속 원리 : 안전하게 서버 문 열기
클라우드 서버가 준비되었으니 접속을 해야 합니다. 인프라 엔지니어라면 무작정 명령어를 복붙하기보다 인증 원리를 이해하고 있어야 트러블슈팅이 가능하겠죠?
SSH(Secure Shell, 포트 번호 22)는 원격 서버의 터미널을 암호화된 채널로 제어하는 프로토콜입니다. 클라우드 환경에서는 패스워드 브루트포스(무차별 대입) 공격을 막기 위해 **비대칭키 기반의 키페어(Keypair) 방식**을 기본으로 사용합니다.
키페어는 수학적으로 완벽하게 짝지어진 두 개의 키로 구성됩니다.
- **🔒 공개키 (Public Key / 자물쇠)** : 서버를 생성할 때 클라우드 인프라가 인스턴스 내부에 미리 주입해 둔다. (~/.ssh/authorized_keys 파일)
- **🔑 개인키 (Private Key / 열쇠)** : 내 로컬 PC에만 보관하는 .pem 파일입니다.
내가 서버에 접속을 시도하면, 서버는 "이 자물쇠를 풀 수 있는지 증명해 봐"라며 암호화된 챌린지(난수)를 던집니다. 내 컴퓨터는 로컬에 있는 개인키를 이용해 이 문제를 풀어내고, 서버는 이를 확인하여 문을 열어줍니다. **네트워크 상으로 비밀번호나 키 자체가 전송되지 않기 때문에 중간자 공격(MITM)에 매우 안전합니다.**
> **⚠️ 보안 주의** : 자물쇠(공개키)는 외부에 퍼져도 무방하지만, **열쇠(개인키)가 유출되면 그 서버는 해커에게 관리자(root) 권한을 넘겨준 것과 같습니다.** 키 파일을 깃허브 퍼블릭 레포지토리에 실수로 커밋하지 않도록 각별히 주의해야 합니다.

### 💻 3. 실습 : 서버 접속 및 스펙 검증
생성한 클라우드 VM의 공인 IP와 다운로드한 개인키 파일(.pem)을 준비합니다. 터미널(macOS/Linux) 또는 PowerShell(Windows)을 열고 접속을 시도해 봅니다.

#### ① 개인키 파일 권한 설정 (macOS / Linux 전용)
```
chmod 600 ~/Downloads/mykey.pem
```
SSH는 보안에 매우 민감합니다. 내 개인키 파일을 시스템의 다른 유저도 읽을 수 있는 권한 상태라면 접속을 아예 거부해버립니다. (WARNING : UNPROTECTED PRIVATE KEY FILE!)
chmod 600은 "이 파일은 오직 소유자인 나만 읽고 쓸 수 있다"고 권한을 엄격하게 제한하는 필수 명령어입니다. _(Windows 사용자는 이 단계를 건너뛰어도 무방합니다.)_

#### ② 서버 접속
```
ssh -i ~/Downloads/mykey.pem ubuntu@<공인IP>
```
- -i : 접속할 사용할 개인키(Identity file)의 경로를 지정합니다.
- ubuntu : Ubuntu Cloud Image 기반 인스턴스의 기본 접속 계정명입니다. (CentOS는 centos, Amazon Linux는 ec2-user 등 OS마다 다릅니다.)
> **💡 최초 접속 시 경고 :**
The authenticity of host ... can't be established 라는 프롬프트가 뜹니다. "이 서버 처음 보는데, 지문(Fingerprint)을 로컬에 등록하고 믿을래?"라는 의미합니다. "yes"를 입력하면 ~/.ssh/known_hosts에 저장되고 다음부터는 묻지 않습니다.

#### ③ 프로비저닝된 인스턴스 상태 검증
무사히 접속되었다면, 내가 클라우드 콘솔에서 요청한 스펙대로 서버가 잘 만들어졌는지 리눅스 명령어로 뜯어봅니다.
```
lsb_release -a                      # OS 버전 확인 (예: Ubuntu 24.04 LTS)
nproc                               # 할당된 코어(vCPU) 개수 확인
free -h                             # 메모리(RAM) 할당량 확인
df -h /                             # 루트 파일시스템 디스크 여유 공간 확인
ip a                                # 할당된 네트워크 인터페이스(eth0)와 내부 IP 확인
egrep -c '(vmx|svm)' /proc/cpuinfo  # 하드웨어 가상화(KVM 가속) 지원 여부 확인
```

> **🔥 가상화 엔지니어를 위한 팁 :**
egrep -c '(vmx|svm)' /proc/cpuinfo 결과가 1 이상이면 물리 CPU의 가상화 확장 기능을 사용할 수 있다는 뜻이고, '0'이면 QEMU 에뮬레이션 모드(소프트웨어 연산)로 동작하고 있다는 뜻입니다. 만약 클라우드 VM 내부에 Docker나 Kubernetes를 올리거나 중첩 가상화를 테스트할 계획이라면 이 결과값을 꼭 확인해야 성능 저하를 막을 수 있습니다.

### 🛠️ 4. 부록 : 자주 만나는 SSH 네트워크 에러 대처법
인스턴스 생성 직후 SSH 접속에 실패하더라도 당황할 필요가 없습니다. 아래의 에러 메시지 표를 숙지하면 트러블슈팅 시간을 획기적으로 줄일 수 있습니다.
| 에러 메시지 | 발생 레이어 | 원인과 의미 | 해결 조치 |
|---|---|---|---|
| Permission denied (publickey) | Application (인증) | 지정한 개인키가 틀렸거나, 접속 계정명(OS별 기본 계정)이 다름 | `-i` 파일 경로와 계정명(예 : ubuntu) 재확인 |
| UNPROTECTED PRIVATE KEY FILE | Client OS | 키 파일 권한이 타인에게 열려 있어 SSH 클라이언트가 보안상 거부함 | 로컬에서 `chmod 600 <키파일>` 실행 후 재시도 |
| Connection timed out | Network (L3~L4) | **"길이 막힘"** (네트워크 패킷이 서버에 도달조차 못함) | 클라우드 보안 그룹(Security Group) 22번 포트 허용 여부, IP 오타, 로컬 방화벽 확인 |
| Connection refused | Application (L7) | **"도착했는데 문전박대"** (서버 앞까지 갔는데 수신 프로세스가 없음) | 인스턴스는 켜졌으나 OS 부팅 및 sshd 데몬 구동 중임. 1~2분 대기 후 재시도! |
> 📌 **핵심 요약** : timed out과 refused의 차이를 꼭 기억하세요! **timed out은 아예 서버 근처도 못 간 네트워크/방화벽 문제**이고, **refused는 서버까지 패킷이 갔는데 문이 닫혀서 튕겨난 문제**입니다. 이 구분 하나로 트러블슈팅의 방향성이 달라집니다.

### 🔍 SSH 접속 결과 상세 분석
#### 1. SSH 호스트 키(Fingerprint) 검증 완료
```
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Warning: Permanently added '1.201.116.77' (ED25519) to the list of known hosts
```
- 클라이언트(내 컴퓨터)가 처음 보는 서버(1.201.116.77)에 젖ㅂ속했기 때문에, 서버가 제시한 공개키의 지문(Fingerprint)을 신뢰할 것인지 물어본 단계입니다.
- yes를 입력하셨기 때문에 이 지문이 로컬 PC의 ~/.ssh/known_hosts 파일에 안전하게 기록되었습니다. 다음번 접속부터는 이 질문 없이 즉시 인증(Handshake)이 진행됩니다.

#### 2. 클라우드 네트워크 아키텍처 (NAT)
- **외부 공인 IP** : 접속하실 때 사용한 타겟 IP는 1.201.116.77입니다.
- **내부 사설 IP** : 하지만 화면 중간의 IPv4 address for eth0 항목을 보면 서버 내부의 실제 IP는 192.168.0.106 (사설 IP)으로 매핑되어 있습니다.
- 이는 클라우드 환경의 전형적인 네트워크 구조로, 외부에서 들어오는 공인 IP(Floating IP)와 내부 VM 실제로 몰려있는 가상 네트워크(Private IP)가 1:1 NAT로 연결되어 있음을 보여줍니다.

#### 3. OS 및 시스템 리소스 상태
- **OS** : Ubuntu 24.04.4 LTS (최신 장기 지원 버전)로 정상 구동 중입니다.
- **디스크 & 메모리** : 루트(/) 파티션은 전체 47.39GB 중 4.5%만 사용 중이며, 메모리 사용량도 4%로 자원이 매우 쾌적한 초기 깡통(Vanilla) 상태임을 알 수 있습니다.
