## B1. "인스턴스 생성" 버튼 뒤의 전체 경로 → *3회차 예고*

Part A에서 배운 부품들을 전부 연결하면, 버튼 하나가 통과하는 경로가 그려집니다:

```
1. Horizon/CLI → Keystone     인증, 토큰 발급
2. → nova-api                 요청 수신, 토큰 검증, DB에 인스턴스 레코드 생성 (상태: BUILD)
3. → nova-conductor/scheduler Placement에서 후보 노드 자원 조회 → Filter/Weigh로 배치 확정
4. → nova-compute             MQ로 "이 노드에 만들어라" 수신
5. → Glance / Neutron / Cinder  이미지 다운로드 · 포트 생성과 IP 할당 · 볼륨 연결(필요 시)
6. → libvirt → QEMU           VM 정의(XML) 작성 → 프로세스 기동 → 상태 ACTIVE
```

단계별로 무슨 일이 실제로 일어나는지 봅시다.

**1~2단계 (수 초)** — 토큰 검증이 끝나면 nova-api는 즉시 DB에 "이런 인스턴스가 생성 중"이라는 레코드를 만들고 상태를 `BUILD`로 둡니다. 이 시점에 Horizon 화면에는 벌써 인스턴스가 보입니다. 아직 아무것도 안 만들어졌는데도요 — 화면에 보이는 것과 실제 존재하는 것의 간극이 여기서 생깁니다.

**3단계 (수 초)** — scheduler가 Placement에 "메모리 512MB, vCPU 1개 여유 있는 노드 목록 줘"라고 물어보고, Filter로 부적합 노드를 걸러낸 뒤 Weigh로 점수를 매겨 한 대를 고릅니다. 우리 실습은 all-in-one(노드 1대)이라 고를 게 없지만, 경로 자체는 똑같이 지나갑니다.

**4~5단계 (수십 초~) — 시간이 실제로 걸리는 구간** — 선택된 노드의 nova-compute가 MQ에서 작업을 받아 준비물을 모읍니다. Glance에서 이미지를 받아오고(처음엔 네트워크 다운로드, 이후엔 로컬 캐시), Neutron에 "포트 하나 만들어 줘"라고 요청해 MAC 주소와 IP를 할당받고, 볼륨이 필요하면 Cinder에 요청합니다.

**6단계** — 준비물이 모이면 libvirt에게 VM 정의 XML을 넘기고, QEMU 프로세스가 뜨면서 상태가 `Spawning` → `ACTIVE`로 바뀝니다. 6회차에 Horizon에서 이 상태 변화를 실시간으로 관찰합니다.

**로그로 추적하기** — 이 모든 단계는 각 서비스의 로그에 남습니다. Kolla 환경 기준 `/var/log/kolla/nova/`, `/var/log/kolla/neutron/` 등에 서비스별로 쌓입니다. 7회차 심화 미션이 "인스턴스 하나 만들면서 이 경로를 로그로 따라가기"입니다. 요청마다 붙는 `req-xxxxx` 형식의 request-id를 grep 하면 여러 서비스에 흩어진 한 요청의 흔적을 이어 붙일 수 있습니다.

## B2. Neutron 내부 — OVS 방식 vs OVN 방식 → *6회차 연결*

우리 스터디는 설정 파일(globals.yml)에 `neutron_plugin_agent: "openvswitch"`를 명시해 **OVS 방식**을 씁니다 (Kolla-Ansible 22.0.0의 기본값도 openvswitch지만, 선택 의도를 드러내기 위해 적어둡니다). 6회차 실습이 이 구조를 전제로 하기 때문인데, 이 절을 읽으면 그 선택의 이유까지 보입니다.

### 먼저 알아야 할 개념 두 개

**가상 스위치(vSwitch)** — 물리 스위치가 여러 컴퓨터를 연결하듯, 가상 스위치는 한 서버 안의 여러 VM을 소프트웨어로 연결합니다. 리눅스에는 두 가지가 있는데, 기본 L2 스위칭만 하는 단순한 **Linux Bridge**와, VLAN·터널링·QoS·OpenFlow 제어까지 되는 고급형 **Open vSwitch(OVS)**입니다. Neutron의 핵심 엔진이 OVS입니다.

**네트워크 네임스페이스(netns)** — 리눅스 커널 기능으로, 한 서버 안에 서로 격리된 "미니 네트워크 세계"를 여러 개 만들 수 있습니다. 각 네임스페이스는 자기만의 인터페이스, 라우팅 테이블, 방화벽 규칙을 가집니다. Neutron은 이걸로 가상 라우터를 구현합니다 — 라우터 장비를 사는 게 아니라, netns 하나 만들고 그 안에 라우팅 규칙을 넣는 거죠. `ip netns` 명령으로 목록을 보고 `ip netns exec <이름> <명령>`으로 그 세계 안에서 명령을 실행할 수 있습니다. **6회차에 여러분이 직접 가상 라우터의 netns 안에 들어가 봅니다.**

### OVS 방식 (전통적 구조) — 우리가 쓰는 것

**제어 흐름 (Control Plane)**: 사용자가 "네트워크 만들어 줘"라고 요청하면

```
neutron-server (REST 수신, 논리 네트워크를 DB에 기록)
  → ML2 플러그인 (mechanism driver = openvswitch)
  → RabbitMQ (각 노드의 에이전트에게 RPC로 전달)
```

**실행 (Data Plane)**: 각 노드에 상주하는 에이전트들이 명령을 받아 실제 작업을 합니다

- **neutron-ovs-agent**: RPC를 받아 `ovs-vsctl`, `ovs-ofctl` 명령으로 OVS 설정을 직접 변경
- **neutron-l3-agent**: netns 안에 가상 라우터를 만들고 라우팅·NAT 규칙 관리
- **neutron-dhcp-agent**: netns 안에 DHCP 서버(dnsmasq)를 띄워 인스턴스에 IP 자동 배부

OVS에는 역할이 나뉜 브리지 3개가 만들어집니다:

| 브리지 | 역할 |
| --- | --- |
| **br-int** | 통합 브리지. 모든 VM의 가상 NIC이 여기 연결됨 |
| **br-tun** | 터널 브리지. 다른 노드와의 오버레이 터널(VXLAN 등) 담당 |
| **br-ex** | 외부 브리지. 외부망으로 나가는 출구. Floating IP 트래픽이 여기를 지남 |

핵심 특징: **모든 노드에 에이전트가 상주**하고, neutron-server가 변경사항을 RabbitMQ로 각 에이전트에게 밀어(push) 보내는 **명령형** 구조입니다.

### OVN 방식 (현대적 구조)

OVN(Open Virtual Network)은 같은 문제를 다르게 풉니다. RabbitMQ도, 노드별 여러 에이전트도 없앴습니다.

```
neutron-server → ML2 (driver = ovn)
  → Northbound DB   "이런 논리 네트워크를 원해" (스위치/라우터/ACL 정의)
  → ovn-northd      논리 정의를 실행 가능한 Logical Flow로 번역
  → Southbound DB   Logical Flow + 어느 VM이 어느 호스트에 있는지(Port Binding)
  → 각 노드의 ovn-controller가 SB DB를 구독하다가, 변경을 감지하면
    자기 노드의 OVS에 플로우를 스스로 주입
```

NB/SB 두 DB로 나눈 이유는 **논리와 물리의 분리**입니다. NB에는 "프론트엔드 네트워크와 백엔드 네트워크를 라우터로 잇고 포트 80만 허용" 같은 순수한 의도만 있고, VM이 실제로 어느 서버에 있는지는 전혀 없습니다. SB가 그 의도를 "각 호스트가 해야 할 일"로 풀어놓은 곳이고, 논리 포트↔물리 호스트를 잇는 **Port Binding**이 둘 사이의 연결고리입니다.

이 구조를 **선언형**(declarative)이라고 부릅니다 — "이렇게 됐으면 좋겠다"를 선언하면 시스템이 알아서 그 상태로 수렴시키는 방식. Kubernetes를 써본 분이라면 desired state → reconcile 루프와 완전히 같은 철학임을 알아보실 겁니다.


### 비교와 우리의 선택

| 비교 | OVS 방식 | OVN 방식 |
| --- | --- | --- |
| 전달 방식 | RabbitMQ RPC (밀어주기) | DB 구독 (감시하다 알아서) |
| 노드 에이전트 | ovs-agent + l3-agent + dhcp-agent | ovn-controller 하나 |
| L3 라우팅 | l3-agent가 netns로 구현 | OVN 내장 분산 라우팅 (netns 없음) |
| 상태 모델 | 명령형 | 선언형 |
| 대규모 확장 | RabbitMQ가 병목 가능 | DB 기반이라 유리 |

신규 대규모 배포라면 OVN이 대세입니다. 그런데 우리는 굳이 OVS 방식을 택했습니다. 이유는 표의 "L3 라우팅" 줄에 있습니다 — **OVN은 가상 라우터를 netns 없이 구현하기 때문에, 6회차의 "netns 안에 들어가 가상 라우터 실체 보기" 실습이 OVN에서는 불가능**합니다. 학습 목적에는 구조가 눈에 만져지는 OVS 방식이 낫다는 판단입니다. 기술 선택에 "더 최신"이 아니라 "목적 적합"이 기준이 된 사례이기도 합니다.

## B3. 오버레이 네트워크 — 서로 다른 서버의 VM이 한 네트워크에 있는 척하는 법

**문제 상황**: VM-A는 서버1에, VM-B는 서버2에 있습니다. 둘은 같은 가상 네트워크(10.0.0.0/24)에 속해 있고, 서로 옆자리인 줄 압니다. 하지만 실제 두 서버 사이에는 물리 네트워크(예: 192.168.1.0/24)가 있고, 물리 라우터는 10.0.0.0/24라는 대역의 존재조차 모릅니다. VM-A가 10.0.0.6으로 패킷을 보내면 물리 네트워크는 어디로 보내야 할지 모릅니다.

**해법 — 캡슐화(Encapsulation)**: VM의 패킷을 통째로, 물리 네트워크용 패킷 안에 "포장"해서 보냅니다.

VM-A가 보낸 원본 패킷:

```
[Ether: src=VM-A MAC, dst=VM-B MAC]
[IP:    src=10.0.0.5, dst=10.0.0.6]
[페이로드]
```

서버1의 OVS가 이걸 포장한 결과:

```
[Ether: src=서버1 MAC, dst=서버2 MAC]      ← 물리 계층
[IP:    src=192.168.1.11, dst=192.168.1.12] ← 물리 IP
[UDP:   dst port 4789(VXLAN) / 6081(Geneve)]
[터널 헤더: VNI(가상 네트워크 번호), ...]
[원본 패킷 전체]                             ← 페이로드로 통째 삽입
```

물리 네트워크 눈에는 그냥 "서버1이 서버2에게 보내는 평범한 UDP 패킷"입니다. 서버2의 OVS가 받아서 포장을 벗기고, 터널 헤더의 **VNI**(Virtual Network Identifier, 가상 네트워크 번호표)를 보고 "이건 5번 가상 네트워크 것"임을 알아낸 뒤, 그 네트워크에 속한 VM-B에게 전달합니다. VM-B는 포장이 있었는지도 모릅니다. 이렇게 물리망 위에 가상망을 얹는 것을 **오버레이(overlay) 네트워크**, 그 포장 방식을 **터널 프로토콜**이라 합니다. B2에서 본 br-tun 브리지가 바로 이 포장/해체 담당입니다.

### 터널 프로토콜 비교 — VXLAN은 왜 나왔고 Geneve는 왜 또 나왔나

**VXLAN이 나온 배경** — 원래 네트워크 분리는 VLAN(B4에서 설명)으로 했는데, VLAN ID가 12비트라 최대 4,096개뿐입니다. 클라우드에서는 테넌트마다 네트워크를 주니 금방 바닥나죠. 또 가상화로 VM이 폭증하면서 물리 스위치가 기억해야 할 MAC 주소가 감당 불가 수준이 됐습니다. VXLAN은 VNI를 24비트(약 1,600만 개)로 늘리고, MAC 주소 관리를 물리 스위치에서 각 서버의 vSwitch로 옮겨 두 문제를 해결했습니다.

**Geneve가 또 나온 이유** — VXLAN 헤더는 크기가 고정이라 VNI 말고는 아무 정보도 실을 수 없습니다. Geneve는 **가변 길이 옵션 필드**를 둬서 헤더에 추가 메타데이터를 실을 수 있게 했습니다. OVN이 Geneve를 기본으로 쓰는 이유가 이것인데, 옵션에 "이 패킷은 논리 포트 X에서 나와 논리 포트 Y로 간다"를 실어 보내면 수신 측이 재계산 없이 즉시 논리 흐름을 이어갈 수 있기 때문입니다.

| 항목 | GRE | VXLAN | Geneve |
| --- | --- | --- | --- |
| 전송 | IP 위 직접 | UDP 4789 | UDP 6081 |
| 네트워크 ID | 32bit (Key) | 24bit VNI | 24bit VNI |
| 헤더 | 4~8B | 8B 고정 | 8B + 가변 옵션 |
| 확장성 | 거의 없음 | 없음 | 우수 |
| 표준 | RFC 2784 | RFC 7348 | RFC 8926 |

## B4. 네트워크 가상화 개념 지도 — 용어 정리

위에서 지나간 용어들을 지도로 정리합니다.

**VLAN (Virtual LAN)** — 물리적으로는 한 스위치에 물려 있어도 논리적으로 별개 네트워크처럼 분할하는 기술. 이더넷 프레임에 4바이트짜리 802.1Q 태그를 끼워 넣고, 그 안의 12비트 VID로 소속 VLAN을 구분합니다. 원래 목적은 브로드캐스트 도메인 분리 — ARP 같은 브로드캐스트가 네트워크 전체에 퍼지는 걸 막는 것입니다. 한계(4,096개)는 B3에서 본 대로 VXLAN 등장의 배경이 됐습니다.

**vSwitch** — 서버 안의 소프트웨어 스위치. VM의 가상 NIC(vNIC)을 물리 NIC과, 그리고 서로와 연결합니다. 물리 스위치처럼 Access Port(태그 없이 단일 VLAN 소속)와 Trunk Port(여러 VLAN 태그를 함께 통과) 개념이 그대로 있습니다. Linux Bridge(단순형)와 Open vSwitch(고급형)가 대표적이며 Neutron은 OVS를 씁니다.

**SDN (Software-Defined Networking)** — 네트워크의 **제어부**(어디로 보낼지 결정하는 두뇌, Control Plane)와 **전송부**(실제로 패킷을 나르는 손발, Data Plane)를 분리하고, 제어부를 소프트웨어로 중앙화하는 아키텍처입니다. 전통 네트워크는 스위치마다 두뇌가 박혀 있어 장비를 하나하나 설정해야 했는데, SDN에서는 중앙 컨트롤러가 전체 그림을 보고 각 장비에 규칙을 내려보냅니다. 대표 프로토콜이 OpenFlow입니다. **Neutron 자체가 SDN 컨트롤러 역할**입니다 — 논리 네트워크 정의(제어)를 받아 각 노드의 OVS(전송)에 반영하니까요.

**NFV (Network Function Virtualization)** — 방화벽, 로드밸런서, 라우터처럼 전용 하드웨어 장비로 팔리던 네트워크 "기능"을 범용 서버 위의 소프트웨어(VM/컨테이너)로 구현하는 것입니다. SDN이 "네트워크를 쉽게 제어하자"라면 NFV는 "네트워크 장비를 소프트웨어로 만들자"이고, 둘은 상호 보완 관계입니다. Neutron의 가상 라우터(netns + 라우팅 규칙)가 NFV의 좋은 예시입니다 — 라우터 장비 없이 라우터 기능을 소프트웨어로 만든 거니까요.

## B5. Ceph 개요 — 프로덕션 스토리지의 표준 → *실무 확장 지식*

우리 all-in-one 실습은 Cinder를 끄고 인스턴스 디스크를 nova의 로컬 ephemeral qcow2 파일로만 쓰지만, 실제 프로덕션 OpenStack의 스토리지 백엔드는 **Ceph**가 사실상 표준입니다. 구조만 알아둬도 실무 문서를 읽을 때 큰 차이가 납니다.

Ceph는 오픈소스 분산 스토리지로, 여러 서버의 디스크를 묶어 하나의 거대한 저장소를 만들고 오브젝트/블록/파일 세 가지 방식으로 제공합니다.

**구성 데몬**

| 데몬 | 역할 |
| --- | --- |
| **MON** (Monitor) | 클러스터 상태와 배치 지도(맵) 관리. 여러 MON이 Paxos 합의 알고리즘으로 "지금 클러스터 상태가 무엇인지"에 대한 일치를 보장 |
| **OSD** (Object Storage Daemon) | 실제 데이터가 저장되는 곳. 디스크 하나당 OSD 하나가 붙어 저장·복제·리밸런싱·복구를 수행 |
| **MDS** | CephFS(파일시스템)용 메타데이터 관리 |
| **MGR** | 운영 메트릭 수집, MON의 부하 분산 |

**세 가지 인터페이스**

- **RGW**: 오브젝트 스토리지 게이트웨이. S3 호환 API 제공
- **RBD** (RADOS Block Device): 블록 스토리지. **OpenStack과의 접점이 여기** — Cinder 볼륨과 Glance 이미지의 백엔드로 쓰이며, 프로덕션에서 VM 디스크는 대부분 RBD에 저장됩니다
- **CephFS**: POSIX 호환 파일시스템

**저장 원리 — CRUSH 알고리즘**: 파일이 들어오면 여러 오브젝트로 쪼개지고, 각 오브젝트는 CRUSH라는 알고리즘으로 저장 위치(어느 OSD들)가 **계산**됩니다. 핵심은 "어디 저장돼 있는지 기록해 둔 중앙 조회 테이블이 없다"는 것 — 클라이언트가 오브젝트 ID만 알면 위치를 스스로 계산해 해당 OSD에 직접 요청합니다. 조회 서버라는 병목이 없어서 수천 대 규모까지 확장되는 비결입니다. 모든 오브젝트는 여러 OSD에 복제 저장되어 디스크 몇 개가 죽어도 데이터가 살아남습니다.

## B6. 배포 도구 비교 — 왜 Kolla-Ansible인가

같은 OpenStack이라도 설치하는 방법이 여럿 있고, 각자 목적이 다릅니다.

| 방식 | 구조 | 용도 | 한계 |
| --- | --- | --- | --- |
| **DevStack** | `stack.sh` 스크립트 하나로 소스에서 전부 설치 | 개발·테스트·빠른 학습 | 재부팅하면 서비스가 깨짐. 운영 불가 |
| **Kolla-Ansible** | 서비스마다 Docker 컨테이너로 배포, Ansible이 전체 오케스트레이션 | 준운영~운영 | DevStack보다 준비 단계 많음 |
| **수동 설치** | 공식 설치 가이드 따라 컴포넌트 하나씩 직접 구성 | 구조를 뼛속까지 이해하는 학습 | 시간 비용이 매우 큼 |
| **OpenStack-Helm** | Kubernetes 위에 Helm 차트로 배포 | 대규모 운영 | K8s 클러스터가 전제 |

우리가 Kolla-Ansible을 택한 이유:

1. **구조가 눈에 보입니다** — 서비스=컨테이너 매핑이라 `docker ps` 한 번으로 아키텍처 전체가 화면에 나열됩니다. Part A에서 배운 그림이 그대로 보이는 거죠
2. **멱등(idempotent)합니다** — 같은 배포 명령을 다시 실행해도 안전하고, 중간에 실패해도 원인 고치고 재실행하면 이어서 갑니다. 실습에서 실패가 치명상이 아니게 되는 성질입니다
3. **실무 도구입니다** — 실제 운영 환경에서 쓰이는 배포 방식이라, 스터디 경험이 그대로 이력이 됩니다
