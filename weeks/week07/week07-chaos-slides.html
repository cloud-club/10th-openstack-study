한 라운드는 이렇게 돈다

1. 주입리더가 여러분 VM에 원격으로 장애를 넣는다
2. 증상뭐가 안 되는지부터. 목록, 새 VM, SSH
3. 추적진단 도구로 몇 단계에서 끊겼는지
4. 채팅 한 줄"○단계, ○○가 죽었다". 찾은 방법은 비밀
5. 복구고쳐 보고 정상 동작 확인
  • 못 고쳐도 괜찮습니다. 라운드가 끝나면 리더가 일괄 복구합니다.
  • 5분 넘게 단서가 하나도 안 보이면 손 들기. 힌트 드립니다.
  • 에러 화면은 캡처해 두세요. 8회차 발표 소재가 됩니다.

$ source ~/kolla-venv/bin/activate
$ source /etc/kolla/admin-openrc.sh                  # 출입증. 지금 미리 쳐 두기

# ④ 로그
$ sudo grep -iE "error|fail|timeout" /var/log/kolla/nova/*.log | tail -n 20

  • 에러 문구는 마지막 줄부터 읽습니다. 숫자 하나가 눈에 띌 거예요.
  • 찾으면 채팅에 "○단계, ○○가 죽었다" 한 줄.

풀이 8분. 첫 라운드는 같이 풉니다.

라운드 1 해설

1단계, 출입증 창구가 문을 닫았다

$ openstack server list
Failed to discover available identity versions when contacting http://<VIP>:5000 ...
... Failed to establish a new connection: [Errno 111] Connection refused

$ docker ps -a --format "table {{.Names}}\t{{.Status}}" | grep -v " Up "
keystone          Exited (0) 7 seconds ago
:5000
Keystone 포트. 어느 서비스를 부르다 실패했는지 알려 준다.
refused
그 주소까지는 갔는데 듣고 있는 프로그램이 없다. 서비스 쪽을 의심.
복구
sudo systemctl start kolla-keystone-container

그런데 docker stop으로는 장애가 안 났습니다

# 리허설: docker stop keystone 직후
$ openstack server list
| first-vm | ACTIVE | ...      ← 그냥 됨

$ docker ps --filter name=keystone
keystone   Up 52 seconds (healthy)

$ systemctl list-units 'kolla-*' | grep keystone
kolla-keystone-container.service
           loaded active running

Kolla는 컨테이너마다 systemd 유닛을 만들어 지킨다. docker로 끄면 systemd가 바로 다시 띄운다.

진단 도구에 추가:
systemctl list-units --all 'kolla-*' | grep -v running

운영 질문: 죽은 프로세스는 누가 살리고, 살아났다는 걸 누가 알려 주나?

라운드 2

이번엔 사람마다 다른 장애 (3종 중 하나)

$ openstack server create chaos-test --image cirros --flavor m1.tiny \
    --network tenant_network --key-name mykey
$ watch -n 5 openstack server list          # Ctrl+C로 빠져나오기
$ openstack server show chaos-test -c status -c created -c updated -c fault
  • BUILD에서 멈춘 것 같아도 1~2분은 기다리기. 기다려야 보이는 장애가 있습니다.
  • fault가 진짜 원인이 아닐 수 있습니다. 서비스 상태와 로그까지 가 보기.
  • 옆 사람과 답이 다를 수 있어요. 채팅엔 "○단계, 원인" 한 줄만.

풀이 13분. 일찍 끝낸 분께는 보너스 장애를 하나 더 넣어 드립니다.

created  04:47:51Z

라운드 2 해설 ③

5단계, fault에서 멈추면 틀린다

① server show 의 faultMaxRetriesExceeded
"호스트를 다 써 버렸다" → 호스트 부족? 함정
② nova-compute.logPortBindingFailed
"please check neutron logs" 다음 행선지를 알려 준다
③ network agent listOpen vSwitch agent XXX
포트를 실제로 꽂는 일꾼이 죽었다
$ sudo grep -i binding /var/log/kolla/nova/nova-compute.log | tail -n 3
nova.exception.PortBindingFailed: Binding failed for port b62d...,
please check neutron logs for more information.

fault는 마지막에 포기한 이유, 처음 실패한 이유는 로그에. 복구: sudo systemctl start kolla-neutron_openvswitch_agent-container

같은 "VM이 안 만들어진다", 다른 세 곳

장애실패까지첫 단서끊긴 곳
quota즉시403 ... :8774 생성 명령에서 바로2단계 접수
nova_scheduler 정지약 60초fault MessagingTimeout3단계 배치 결정
OVS agent 정지약 20초compute 로그 PortBindingFailed5단계 준비물

바로 거절되면 앞쪽에서 막힌 것, 한참 기다리다 실패하면 대답 안 하는 누군가가 있는 것.

$ openstack server delete chaos-test       # 리더 일괄 복구 후 정리

라운드 3 해설

로그에 아무것도 남지 않는 장애

$ ssh -i ~/mykey.pem cirros@192.168.200.1xx
ssh: connect to host 192.168.200.1xx port 22: Connection timed out

$ openstack security group rule list default --protocol tcp
More than one SecurityGroup exists with the name 'default'.   ← 프로젝트마다 하나씩
$ SG=$(openstack security group list --project admin -f value -c ID -c Name | awk '$2=="default"{print $1}')
$ openstack security group rule list $SG --protocol tcp
(비어 있음)     ← 22번 규칙이 사라졌다
timed out
중간에서 패킷이 버려졌다. 방화벽, 보안그룹을 의심. (1라운드 refused와 반대)
복구
openstack security group rule create --protocol tcp --dst-port 22 $SG
