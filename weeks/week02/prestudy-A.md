# Part A — 필수

## A1. OpenStack이란 무엇인가

OpenStack 공식 소개는 이렇습니다:

> "데이터센터 전반에 걸쳐 있는 대규모의 컴퓨팅, 스토리지, 네트워킹 자원 풀(pool)을 제어하는 클라우드 운영체제이며, 이 모든 자원은 공통된 인증 메커니즘을 갖춘 API를 통해 관리되고 프로비저닝된다."
> 

이 한 문장을 뜯어보면 OpenStack의 거의 전부가 들어 있습니다.

**"클라우드 운영체제"** — 리눅스 같은 일반 OS는 한 대의 컴퓨터 안에서 CPU·메모리·디스크를 여러 프로세스에게 나눠줍니다. OpenStack은 같은 일을 데이터센터 규모에서 합니다. 서버 수십~수천 대의 CPU·메모리·디스크·네트워크를 하나의 커다란 자원 풀로 묶고, 그걸 여러 사용자(테넌트)에게 나눠주는 거죠. 그래서 스스로를 "운영체제"라고 부릅니다.

**"프로비저닝(provisioning)"** — 자원을 준비해서 사용 가능한 상태로 만들어 주는 것. AWS에서 인스턴스 생성 버튼을 누르면 몇십 초 뒤 SSH 가능한 서버가 생기는 것, 그게 프로비저닝입니다.

**"공통된 인증 메커니즘을 갖춘 API"** — OpenStack에서 일어나는 모든 일은 API 호출입니다. 웹 대시보드(Horizon)에서 버튼을 누르든, 터미널에서 CLI를 치든, 파이썬 SDK를 쓰든, 최종적으로는 전부 같은 REST API가 호출됩니다. 그리고 그 모든 호출은 단 하나의 인증 서비스(Keystone)를 통과해야 합니다. "버튼과 명령어는 다르게 생겼지만 뒤에서는 같은 API"라는 사실은 7회차 보너스 미션(브라우저 F12 Network 탭)에서 직접 확인합니다.

정리하면: **OpenStack은 AWS나 KakaoCloud 같은 IaaS 클라우드를 내 서버에 직접 만들 수 있게 해주는 오픈소스 플랫폼**입니다. 여기서 IaaS(Infrastructure as a Service)란 서버·스토리지·네트워크 같은 인프라 자원을 가상화해 서비스로 제공하는 형태를 말합니다. OpenStack을 돌리는 순간 여러분은 클라우드의 "사용자"에서 클라우드 "사업자(CSP)"로 입장이 바뀝니다.

### 릴리스 모델 — 우리가 배포하는 버전의 정체

OpenStack은 6개월마다(매년 4월, 10월) 새 버전이 나오고, 버전명은 `연도.차수` 형식입니다(2025.1, 2025.2, 2026.1…). 각 버전에는 알파벳 순서의 코드네임이 붙습니다.

우리가 5회차에 배포하는 버전은 **2026.1 "Gazpacho"** 입니다. 2026년 4월에 나온 33번째 릴리스로, 약 500명의 기여자와 100여 개 조직(Red Hat, Samsung SDS, SAP, NVIDIA 등)이 참여했습니다. `setup.sh`가 내부에서 Kolla-Ansible의 `stable/2026.1` 브랜치를 사용하므로, 여러분이 배포하는 게 바로 이 버전입니다.

## A2. 핵심 컴포넌트 — 각자 무슨 일을 하는가

OpenStack은 하나의 프로그램이 아니라 **역할이 나뉜 독립 서비스들의 집합**입니다. 각 서비스는 별도 프로세스로 돌고, 자기만의 API와 DB를 가집니다. 스터디에서 다루는 것은 다음 6개 + 1개입니다.

| 컴포넌트 | 역할 한 줄 | API 포트 | AWS 대응 |
| --- | --- | --- | --- |
| Keystone | 인증·인가 | 5000 | IAM |
| Nova | VM 생명주기 | 8774 | EC2 |
| Neutron | 네트워크 | 9696 | VPC |
| Glance | 부팅 이미지 | 9292 | AMI |
| Cinder | 블록 스토리지 | 8776 | EBS |
| Horizon | 웹 대시보드 | 80/443 | Console |
| Placement | 자원 인벤토리 | 8778 | — |

표만 보면 안 와닿으니, 하나씩 실제로 뭘 하는지 봅시다.

**Keystone (Identity)** — 사용자 계정, 프로젝트(테넌트), 역할(role)을 관리하고, 로그인하면 **토큰**을 발급합니다. 이후 모든 API 요청에는 이 토큰이 첨부되고, 각 서비스는 요청을 처리하기 전에 Keystone에 토큰 유효성을 확인합니다. AWS에서 IAM 권한 없이는 아무것도 못 하는 것과 같은 구조라서 "모든 요청의 관문"이라 부릅니다. 자세한 흐름은 A3에서.

**Nova (Compute)** — VM(인스턴스)의 생성·스케줄링·중지·삭제, 즉 생명주기 전체를 관리합니다. 주의할 점: Nova는 VM을 "직접" 만들지 않습니다. 어느 서버에 만들지 결정하고, 하이퍼바이저(A4에서 설명)에게 "만들어라"고 시키는 관리자입니다. 이 구분이 A4의 핵심입니다.

**Neutron (Networking)** — VM들이 쓸 가상 네트워크를 만들고 관리합니다. 다루는 자원이 여러 개인데, 6회차에 `init.sh`가 만들어주고 여러분이 Horizon Network Topology에서 확인할 것들이라 미리 정의를 알아두면 좋습니다:

- **Network**: 가상의 L2 네트워크. "가상 스위치 하나"라고 생각하면 됩니다
- **Subnet**: 그 네트워크에서 쓸 IP 대역 정의 (예: 10.0.0.0/24)
- **Router**: 네트워크와 네트워크, 또는 내부 네트워크와 외부망을 잇는 가상 라우터
- **Security Group**: 인스턴스 단위 방화벽 규칙 ("TCP 22 인바운드 허용" 같은)
- **Floating IP**: 외부에서 접근 가능한 IP를 인스턴스에 붙였다 뗐다 할 수 있는 공인 IP 개념. 6회차 최종 목표인 `ssh cirros@<Floating IP>`의 그 Floating IP입니다

**Glance (Image)** — VM을 부팅할 때 쓰는 OS 이미지(디스크 템플릿)를 등록·저장·조회합니다. AWS의 AMI에 해당합니다. 우리 실습에서는 **CirrOS**라는 초경량 테스트용 리눅스 이미지(약 20MB)를 씁니다. 이미지 포맷으로는 qcow2(QEMU 표준, 압축·스냅샷 지원)가 가장 흔합니다.

**Cinder (Block Storage)** — 인스턴스에 붙이는 볼륨(가상 디스크)을 관리합니다. AWS EBS처럼, 인스턴스를 지워도 볼륨은 남길 수 있고 다른 인스턴스에 옮겨 붙일 수 있습니다. 인스턴스 자체의 기본 디스크(ephemeral disk, 인스턴스 삭제 시 같이 삭제됨)와 구분됩니다.

**Horizon (Dashboard)** — 웹 UI입니다. Django(파이썬 웹 프레임워크)로 만들어졌고, 내부적으로는 여러분이 CLI로 칠 수 있는 것과 똑같은 API를 호출하는 클라이언트일 뿐입니다. 5회차 배포 후 `http://<공인IP>`로 접속하는 게 이겁니다.

**Placement** — 각 서버에 CPU·메모리·디스크가 얼마나 남았는지 추적하는 자원 장부입니다. 원래 Nova의 일부였다가 분리됐고, Nova가 "이 VM을 어디에 놓을까"를 결정할 때 Placement에 물어봅니다.

실제 OpenStack 2026.1 릴리스에는 서비스 프로젝트만 30개가 넘습니다. 몇 개만 봐도 패턴이 보입니다:

## A3. 서비스들은 어떻게 대화하는가

수십 개의 독립 서비스가 하나의 클라우드처럼 움직이려면 소통 방법이 필요합니다. OpenStack은 상황에 따라 두 가지를 씁니다.

### ① 서비스와 서비스 사이: REST API

REST API란 HTTP 프로토콜(웹브라우저가 쓰는 그것)로 자원을 조회·생성·삭제하는 방식입니다. `GET /servers`는 "서버 목록 줘", `POST /servers`는 "서버 만들어 줘"가 됩니다. 여러분이 치는 CLI 명령은 전부 이 REST 호출로 번역됩니다:

```bash
openstack server list
# ↓ 내부적으로 실제 전송되는 것
# GET /v2.1/servers HTTP/1.1
# Host: <nova-api 주소>:8774
# X-Auth-Token: gAAAAAB...
```

마지막 줄의 `X-Auth-Token`이 핵심입니다. 모든 요청에 Keystone이 발급한 토큰이 붙습니다. 전체 인증 흐름은 이렇습니다:

```
1. 클라이언트 → Keystone(:5000)   ID/비밀번호 제출 (POST /v3/auth/tokens)
2. Keystone → 클라이언트          토큰 발급 + "서비스 카탈로그" 전달
3. 클라이언트 → nova-api(:8774)   실제 요청 + X-Auth-Token 헤더
4. nova-api → Keystone            "이 토큰 유효해?" 검증
5. 유효하면 요청 처리
```

여기서 두 가지 개념을 짚고 갑니다.

**서비스 카탈로그** — 2단계에서 토큰과 함께 받는 것으로, "Nova는 이 주소, Glance는 저 주소" 하는 전체 서비스의 API 주소 목록입니다. 클라이언트가 각 서비스 주소를 미리 알 필요 없이 Keystone 주소 하나만 알면 되는 구조죠. 배포 후 `openstack catalog list`로 직접 볼 수 있습니다.

**Fernet 토큰** — Keystone이 발급하는 토큰의 기본 방식입니다. 특징은 토큰을 서버 DB에 저장하지 않는다는 것. 토큰 자체가 대칭키로 암호화된 데이터 뭉치(사용자, 프로젝트, 만료 시각 등)라서, 검증할 때 DB를 조회하는 대신 키로 복호화만 하면 됩니다. 이런 방식을 **stateless**(무상태)라고 부르는데, 토큰이 수백만 개 발급돼도 서버 저장소가 커지지 않아 확장에 유리합니다. 웹 개발에서 세션 쿠키 vs JWT의 차이를 아는 분이라면 정확히 같은 구도입니다.

### ② 한 서비스 내부: 메시지 큐 (RabbitMQ)

같은 서비스에 속한 프로세스들끼리(예: nova-api와 nova-compute)는 REST가 아니라 **메시지 큐**로 대화합니다.

메시지 큐란 "우체통"입니다. 보내는 쪽은 메시지를 우체통에 넣고 바로 자기 일을 하러 가고, 받는 쪽은 자기 우체통을 확인해 꺼내 처리합니다. 둘이 동시에 접속해 있을 필요가 없죠. OpenStack이 쓰는 우체국이 **RabbitMQ**이고, 이게 따르는 표준 프로토콜이 **AMQP**(Advanced Message Queuing Protocol)입니다.

RabbitMQ 내부 구조:

```
Producer → Exchange → (Binding 규칙) → Queue → Consumer
```

- **Producer**: 메시지를 발행하는 쪽 (예: "VM 만들어라"를 발행하는 nova-api 쪽)
- **Exchange**: 우체국 분류대. 메시지를 받아 규칙에 따라 알맞은 큐로 보냄
- **Binding**: 그 분류 규칙 ("이 라우팅 키가 붙은 메시지는 이 큐로")
- **Queue**: 우체통. 메시지가 소비될 때까지 보관됨
- **Consumer**: 우체통에서 꺼내 일하는 쪽 (예: nova-compute)

OpenStack은 이 위에 RPC(원격 프로시저 호출)를 얹어 씁니다. 패턴이 두 가지인데, `call`은 보내고 응답을 기다리는 동기 방식, `cast`는 던져놓고 바로 돌아오는 비동기 방식입니다. VM 생성처럼 오래 걸리는 작업은 cast로 처리합니다.

**왜 굳이 REST를 안 쓰고 큐를 쓸까?** VM 생성은 수십 초에서 수 분이 걸립니다. REST처럼 동기로 처리하면 그동안 API 프로세스 하나가 통째로 묶여 있어야 하죠. 큐를 쓰면:

1. **비동기** — api는 메시지를 던지고 즉시 다음 요청을 받을 수 있음
2. **내결함성** — compute가 잠깐 죽어도 메시지는 큐에 남아 있다가 복구 후 처리됨
3. **수평 확장** — 같은 큐를 구독하는 compute 노드를 늘리면 작업이 자동으로 분산됨

이 세 가지는 OpenStack만의 이야기가 아니라 대규모 분산 시스템의 공통 패턴입니다. Kafka를 써본 분이라면 같은 문제의식임을 바로 알아보실 겁니다.

### ③ 공용 인프라 — OpenStack이 아닌데 항상 있는 것들

배포하면 OpenStack 프로젝트가 아닌 소프트웨어도 같이 뜹니다. 각각 없으면 안 되는 이유가 있습니다:

| 구성요소 | 역할 | 없으면? |
| --- | --- | --- |
| **MariaDB** | 모든 서비스의 영속 데이터 저장소. "VM이 몇 개고 상태가 뭔지" 같은 기록 전부. 서비스별로 DB를 분리해 사용(nova DB, neutron DB…) | 모든 서비스가 기억상실. 전체 마비 |
| **RabbitMQ** | 위에서 설명한 서비스 내부 RPC 버스 | 부품 간 업무 전달 불가 |
| **Memcached** | 토큰 검증 결과 등을 메모리에 캐싱. 매 요청마다 Keystone까지 왕복하는 비용 절약 | 성능 저하 |
| **HAProxy** | (다중 노드 배포에서) 모든 API 앞단의 리버스 프록시/로드밸런서. **우리 all-in-one에서는 끄기 때문에 `docker ps`에 안 보입니다** — 서비스들이 VIP(사설 IP)에 직접 바인드 | 다중 노드에서 단일 진입점 상실 |

## A4. Nova 해부 — 하이퍼바이저까지 내려가기

"독립 서비스들의 협력"이 어느 깊이까지 내려가는지 Nova 하나를 해부해 보면 실감이 납니다.

### Nova의 네 부품

Nova는 하나의 프로그램이 아니라 최소 4개의 독립 프로세스입니다:

| 프로세스 | 역할 |
| --- | --- |
| **nova-api** | 접수 창구. REST 요청을 받고 토큰을 검증 |
| **nova-scheduler** | 배치 결정. 어느 서버에 VM을 놓을지 계산 |
| **nova-conductor** | DB 중계. compute가 DB에 직접 접근하지 못하게 중간에서 대신 처리 |
| **nova-compute** | 실제 작업자. 하이퍼바이저를 시켜 진짜 VM을 띄움 |

두 가지가 특히 "왜?"를 부릅니다.

**scheduler는 어떻게 자리를 고르나** — 2단계로 계산합니다. 먼저 **Filter**: 조건에 안 맞는 서버를 탈락시킵니다(메모리 부족, 디스크 부족, 특정 조건 불일치 등). 그다음 **Weigh**: 살아남은 후보들에 점수를 매겨 최적의 한 대를 고릅니다(예: 여유 메모리가 많을수록 높은 점수). 이때 각 서버의 잔여 자원 정보는 Placement에서 가져옵니다.

**conductor는 왜 존재하나** — compute 노드는 수백 대까지 늘어나는데, 그 모든 노드가 중앙 DB에 직접 접속하면 보안상 위험하고(노드 하나가 뚫리면 DB 전체 노출) DB 커넥션도 폭증합니다. 그래서 compute는 DB를 만지고 싶을 때 conductor에게 부탁하고, conductor만 DB에 접근합니다. 일종의 검문소입니다.

이 네 부품끼리는 A3에서 배운 RabbitMQ로 대화하고, 다른 서비스(Glance에서 이미지, Neutron에서 네트워크 포트, Cinder에서 볼륨)와는 REST API로 대화합니다.

### 하이퍼바이저 계층 — VM은 결국 누가 만드나

nova-compute도 VM을 직접 만들지 않습니다. 실제 생성은 하이퍼바이저의 몫입니다.

**하이퍼바이저**란 한 대의 물리 서버 위에 여러 가상머신을 만들고 돌리는 소프트웨어입니다. VMware, VirtualBox도 하이퍼바이저의 일종이고, 리눅스 세계의 표준은 **KVM/QEMU** 조합입니다.

```
nova-compute → libvirt → QEMU/KVM → 실제 VM 프로세스
```

- **libvirt** — 하이퍼바이저 추상화 계층. KVM, Xen, VMware 등 서로 다른 하이퍼바이저를 하나의 공통 API로 다루게 해줍니다. nova-compute는 "KVM 문법"을 몰라도 libvirt에게 표준화된 방식(VM 정의 XML)으로 시키면 됩니다. 터미널에서 쓰는 CLI가 `virsh`입니다.
- **KVM** — 리눅스 커널에 내장된 가상화 모듈. CPU의 하드웨어 가상화 기능(Intel VT-x / AMD-V)을 이용해 VM을 거의 물리 서버 속도로 돌립니다.
- **QEMU** — VM 프로세스를 실제로 실행하는 에뮬레이터. KVM이 있으면 CPU 부분은 하드웨어에 맡기고 나머지(디스크, 네트워크 카드 등)만 에뮬레이션합니다. KVM이 없으면? CPU까지 순수 소프트웨어로 흉내 냅니다. 되긴 되는데 많이 느립니다.

### 중첩 가상화 — 우리 환경이 특별한 이유

우리 실습 환경을 그리면 이렇습니다:

```
[물리 서버 (가비아 데이터센터)]
   └── 가비아 VM (Ubuntu) ← 우리가 3회차에 만드는 것. 이미 KVM 위의 VM
        └── OpenStack (Docker 컨테이너들)
             └── OpenStack이 만드는 인스턴스 ← VM 안의 VM
```

인스턴스는 "VM 안의 VM"입니다. 이걸 **중첩 가상화**(Nested Virtualization)라고 하는데, 안쪽 VM에서도 KVM(하드웨어 가속)을 쓰려면 바깥 하이퍼바이저가 VT-x 기능을 안쪽에 노출해줘야 합니다. 퍼블릭 클라우드는 이걸 막아둔 경우가 많습니다.

확인 방법: VM 안에서 `egrep -c '(vmx|svm)' /proc/cpuinfo` — 결과가 0이면 중첩 가상화 미지원입니다. 그 경우 QEMU가 CPU까지 소프트웨어로 에뮬레이션하는 모드로 돌고, 인스턴스 부팅에 1~2분씩 걸립니다. **느린 것은 고장이 아니라 CPU를 소프트웨어로 흉내 내는 대가**입니다. 원인을 알면 "왜 느려요?"가 "아 QEMU 모드구나"가 됩니다.

### 메모리 이야기 — VM 스펙 16GB를 권장하는 실측 근거

OpenStack 컨트롤 플레인(모든 서비스 + MariaDB + RabbitMQ)은 인스턴스를 하나도 안 띄운 상태에서도 수 GB를 상주 점유합니다. 실제로 6GB VM에 OpenStack을 올리고 인스턴스 3대를 만들었더니 2대만 살아남고 1대가 꺼진 사례가 있습니다. 커널 로그(`dmesg`)를 보니:

```
Out of memory: Killed process (mysqld)
Out of memory: Killed process (qemu-system-x86)
```

리눅스는 메모리가 바닥나면 **OOM Killer**가 가장 메모리를 많이 쓰는 프로세스부터 강제 종료합니다. 여기서 첫 희생자가 mysqld(=모든 서비스의 데이터 저장소!)와 qemu(=인스턴스 본체)였던 겁니다. 이 사례에서 가져갈 것:

1. VM 스펙 16GB 권장은 근거 있는 숫자다
2. "인스턴스가 갑자기 꺼졌다"의 범인이 Nova가 아닐 수 있다 — 증상으로 추측하지 말고 로그(`dmesg`)로 확인하고 좁혀갈 것. 이 원칙은 스터디 내내 반복됩니다
